# 01 · 需求与定位

> 记录日期：2026-10-25
> 来源：与 Claude 的需求讨论（2026-10-25 全天）

---

## 一、痛点（用户原话转写）

我买了很多衣服，觉得都不太搭。

> 不是按照穿搭来购买的衣服，而是在购物网站上看到什么好看就买下来，或者看到什么风格可以就买下来，导致买了很多 T 恤、裤子、上衣、外套等。
>
> 这些外套都是单独买的，导致它们整体搭配会产生一个很大的问题。因为我不会搭配，不知道这些东西怎么搭配才看起来比较好看，有一定的特色和风格。
>
> 目前我的风格就是很随便地搭，都感觉不太好看，并且会纠结每天穿什么、什么衣服配什么裤子，这些东西我都不懂。

拆成三个不同的问题：

| 问题 | 性质 | 产品怎么治 |
|---|---|---|
| **买得散**（库存无结构） | 根因 | 缺口诊断：告诉你缺什么、瓶颈在哪 |
| **不懂规则**（不知道什么配什么） | 根因 | 教学模块：用你自己的衣服当教材 |
| **每天纠结**（决策负担） | 症状 | 组合求解 + 每日建议 |

前两个是根因，第三个是症状。产品要治前两个，第三个会跟着好。

## 二、现状事实

| 项 | 实际情况 |
|---|---|
| 库存规模 | 几十件，**T 恤和裤子偏多**，其他品类少 |
| 使用场景 | 日常 + 外出旅游。**没有特殊场合**（不是面试/相亲这类高意图场景） |
| 使用者 | 最初只服务我自己一个人 |

## 三、定位

**旧定位（已废弃）：** AI 男士穿搭顾问 / 衣橱管理 SaaS。
废弃原因：审美不可编码，结果不稳定、不可复现、没人会照着穿；而且衣橱管理的冷启动成本是这类产品的死因。

**现定位：**

> 从你自己零散买来的衣柜里，求解出可穿的整套组合，用看得见的方式呈现，并教你怎么判断。
>
> **用你自己的衣柜当教材的穿搭教练——它教你怎么判断，同时替你做判断。**

三个关键判断支撑这个定位：

1. **审美不可编码，但搭配的硬约束可以编码。** "不会搭配"拆开看，几乎全部落在可判定的事上（正式度跨度、体量冲突、色彩差异 ΔE00、层次厚薄）。真正需要品味的只剩排序那一步。
2. **规则在前，模型在后。** 硬规则做过滤（确定性、可复现），模型只在少数候选里做排序和解释。反过来的结果没人敢用。
3. **教材必须是用户自己的衣服。** 市面上所有穿搭 App 都在"给你答案"或"给你灵感"。没有一个能"用你的真实库存当例题"。因为没人愿意付入库成本——而我自己愿意，因为我要的两个动机（用好库存 + 学会搭配）叠加，正好抵消了这个成本。

## 四、需求三层

### V1 · 原始需求（只服务我自己）

1. 上传衣服、裤子、鞋子，加上个人身体数据
2. 给出几套不同季节的整体搭配
3. 选中某件单品时，从库里反查能配什么

### V2 · 拓展需求（仍是自用）

4. 买新衣服时的匹配：发电商链接或图片，判断能不能跟现有的配、该买什么风格
5. 更丰富的风格组合

### V3 · 向外（当前版本完成后逐项评估，不是否决）

| 计划 | 内容 | 为什么放到后面 |
|---|---|---|
| 性别扩展 | 从"男士专属"扩到通用（或另开女性版本） | 规则层大部分与性别无关，但身体数据、版型基准要重做一套 |
| 博主生态 | 博主一键导入风格 / 设计并发布，普通用户消费，形成双边 | 需要内容供给与冷启动；单人项目现在做不了 |
| 网购决策 | 发链接或图片，结合个人身材 + 已有衣库判断买不买、怎么配 | 依赖 V2 的新衣匹配先跑通 |
| 社交分享 | 把一套搭配生成图片分享到社交平台 | 分享会反向绑架 M1 范围，必须先有能分享的东西 |

**V1 阶段不讨论这四项。** 任何为了"以后要分享"而提前增加的成本，都要被挡住。但它们不是被否掉的方向，只是还没到时间。

## 五、已确认的设计决策

| 项 | 决策 |
|---|---|
| 3D 建模 | ❌ 不做。人和衣服都要建模，复杂度不划算 |
| 试穿路线 | ✅ 2D |
| 配套范围 | ✅ **整套**（上装 + 下装 + 鞋），不是单件 |
| 谁做试穿模型 | ✅ 不自研，用现成 API |
| 判断界面最终形态 | ✅ **B 档合身图**（用自己的衣服真实像素合成） |
| 过渡形态 | A 档平铺拼图（M1），C 档生成式（M4，仅确认与分享） |
| 三种视图 | ✅ 前端可切换 A / B / C |
| 产品形态 | ✅ PWA 起步，按未来可打包成 App 的结构写；V1 不上架 |
| 偏好调整方式 | ✅ **只加个人标签，不改规则**（V1） |
| 反馈机制 | ✅ 隐性为主（采纳/换一套/划掉单品），规则权重靠采纳数据微调 |
| 每日建议 | ✅ 做，且**提前到 M1**（它是偏好数据入口，不是装饰层） |
| 教学模块 | ✅ 做。规则库与求解器**同源** |
| 身体数据 | ✅ **量人与量衣都做**，不是二选一：量人给身体基准，量衣给版型基准 |
| 尺寸量取 | ✅ 外套量 4 项、裤子量 4 项、内层不量（`length_cm` 可空） |
| 场合取值 | ✅ `日常` / `旅游` / `见人` 三个 |
| 季节判定 | ✅ **地址 → 近 10 年气候 → 当前温度区间**；季节标签仅用于展示 |
| 温度取值 | ✅ 用**体感温度**（`apparent_temperature`），不是气温 |
| 求解方式 | ✅ 暴力枚举 + 槽位约束 + 硬过滤 + 软评分；**必须带渐进放宽、多样性去重、锚定求解**（见 02 第四节） |
| 材质字段 | ✅ `material` 进 M1，人工选；VLM 材质准确率仅约 67%，不能自动填 |
| 流行色 | ⚠️ 进课程，**不进算法** |
| 库存清单 | ❌ 不需要提前知道，由上传数据说话 |

## 六、明确否掉的方案

| 方案 | 否掉理由 |
|---|---|
| 3D 数字人 + 3D 服装建模 | 单张照片重建 3D 衣服至今无可用方案 |
| 自研 VTON 模型 | 论文级方法需要专有数据集和 GPU，团队活 |
| 生成式重绘单品图（Wardrobe 那套） | 会把我的衣服画成理想状态，破坏真实性。**注意：`tandpfun/wardrobe` 有 2250★，但星数不改变这条判断** |
| 流行色驱动推荐 | 我的库存是旧的，2026 流行色跟三年前买的衣服无关 |
| 原生 App 起步 | 拍照和分享用 PWA 都能满足；上架是分发问题，不是 V1 问题 |

> 博主生态**不在**此表：它是 V3 计划，见第四节。这里否掉的是"在 V1 就做"的时机，不是方向。
