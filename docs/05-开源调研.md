# 05 · 开源调研

> 调研日期：2026-10-25。目的：开发前确认哪些逻辑能直接用，哪些必须自己写。
> 结论只认代码和许可证，不认 README 里的宣传词。

---

## 一、结论先行

1. **同题参考实现存在，而且比预期近。** `wubian87/dresser`（MIT）就是"规则过滤优先、模型其次、私人衣橱每天选一套"，连 Open-Meteo 天气和穿着轮换都写完了，有实测文档。
2. **成熟产品级实现也存在。** `Anyesh/wardrowbe`（MIT，799★，FastAPI + Next.js）做完了衣橱打标、LLM 推荐、配对学习和天气选衣。它的**词表、身体槽位模型、配对学习公式**可以直接移植。
3. **纯规则求解器没有现成通用库。** 没有哪个仓库把"色彩/比例/层次"编译成一套可单测的规则库。这部分仍然是我们自己的核心，也仍然是差异化的地方。
4. **视觉链路全部有成熟本地库**：rembg / BiRefNet（抠图）、MediaPipe（关键点）、OpenCV ArUco（标定）、colour-science（色差）。不需要自研。
5. **调研前我们自己的文档有 7 个缺口**（见第七节），其中三个会导致 M1 直接出问题：硬规则全灭时没有退让机制；输出没有去重，37 套里会有大量近似重复；"选中一件 → 配一套"没有对应的求解入口。**这三项已在 `02` / `03` 中补齐**，状态见第七节。
6. **`ideas.md` 里那份 11 项竞品清单，复核后只有 3 项可用**（见二·补）。其中星最多的 `tandpfun/wardrobe`（2250★）恰好走的是被我们列为红线的生成式重绘路线。

**一句话：M1 的骨架大约有 40% 可以移植或依赖现成代码，剩下的规则库和 A/B 视图是我们自己的活。**

### 2·补.1 `tandpfun/wardrobe`（2250★ MIT）—— 星最多，恰恰是我们不能走的路

它的 `import-clothes` Skill 开头就写明目标：把穿在身上的衣服变成"source-faithful transparent catalog PNGs"和"modeled editorial photos"。实现方式是 **gpt-image 重绘**：原照 → 裁切 → 模型生成一张干净透明底单品图 → 再生成一张"穿在参考人身上"的编辑照。

两个问题同时命中我们的红线：

1. **重绘即失真。** 生成图会补出原照片里没有的纹理、纽扣、剪裁；判断依据变成模型想象的那件衣服。
2. **上传第三方。** 全流程依赖 OpenAI Images API，衣柜照片必须上传。

它的 `library.json` 里有个值得一提的简化槽位词表：`upperbody` / `wholebody_up`（外套）/ `lowerbody` / `accessories_up` / `shoes`。比 `wardrowbe` 的 8 角色粗，但足够挡掉"两条裤子"。

> **写进决策记录的一句话：2.2k star 不代表这条路对。** 它的目标用户要的是"好看的展示图"，我们要的是"能判断的真实图"，这是两个产品。

### 2·补.2 `anushreeberlia/loom`（4★ MIT）—— 代码不全，但它做了一次我们正需要的实验

仓库里几乎只有 `app.py`、文档和评测脚本，`services/` 没开源。但 `docs/reports/LOOM_DIAGNOSIS_REPORT.md` 是一份**用 620 件 H&M、1 万道 Polyvore FITB 题跑出来的对照实验**，正好回答了我们争论过的几件事：

| 它做的改动 | 结果 | 对我们的意义 |
|---|---|---|
| 从"规则打分"换成"学习到的打分器" | FITB recall@1 0.509 → 0.424，AUC 0.670 → 0.773，但**学习打分器反而低于纯余弦 0.773 → 0.644** | 学习层不天然优于规则，M4 的权重自适应不该期待大收益 |
| 删掉显式色彩规则、交给嵌入 | 色彩冲突率 0.902 → 0.958（更差） | **色彩必须写成显式规则**，我们的 COL 模块方向正确 |
| 保留硬门槛 | 三套覆盖 2.73 → 2.40，"all candidates violated hard gates, skipping" | 硬门槛会吃掉产出 → 印证必须做**渐进放宽**，而不是直接返回空 |
| 用同一套向量表达"相似 / 适合上班 / 配牛仔裤" | 它自己的诊断：一个 512 维向量分不开这几件事 | 我们不做嵌入检索，是对的 |

它最后给出的修复方案是"**恢复色彩与互补规则过滤器**"——一个 2k 行规则代码的项目，绕了一大圈回到规则。

### 2·补.3 `jahid4k/chromafit`（0★，无许可证）—— 概念好，数据是假的

它是唯一一个把"色彩关系"做成第一公民的项目，三个可取之处：

1. **六类色彩关系**：`analogous` / `complementary` / `triadic` / `split-complementary` / `monochromatic` / `neutral`。这是一套现成的、可教学的色彩词汇，比我们现在的"明度差 15"更接近人话。**建议只用在解释文案和 M3 课程里，不新增规则。**
2. **锚定模式**：指定一件为锚，只在它周围补 1–3 件。这正是 V1 第三项需求"选中一件 → 配一套"。
3. **ΔE2000 打分**：`min ΔE(item, palette)` 取平均，再线性映射到 0–80 分。做法与我们 4.2 的设想一致，可以互证。

但要纠正 `ideas.md` 里的一处说法：**它的 `sanzo_wada_palettes.json` 不是《配色辞典》的数据。** 实际只有 30 个调色板、114 个颜色，命名是 "Midnight Dusk"、"Autumn Ember" 这类现代英文名，色值直接取自 CSS 命名色（如 #8B4513 Saddle Brown）。真正的 Wada 是 348 组、有日文原名。**这条数据不能当权威用。**

另外它没有许可证，代码不能抄；组合逻辑也很浅：2–4 件、每类至多一件、无层次、无正式度、无身体。它只是在色彩一个维度上比我们细。

### 2·补.4 `leoz9/AIWardrobe`（186★ MIT，中文）—— 技术栈与我们几乎一样

FastAPI + React + SQLite + rembg 本地抠图 + Open-Meteo + OpenAI 兼容接口。可抄的具体点：

| 它做的 | 我们该怎么用 |
|---|---|
| 温度用**体感温度**（feels-like）而非气温，五档（≤5 / ≤14 / ≤24 / ≤30 / >30） | 我们的四档改用 `apparent_temperature`，边界值可参考 |
| 地点解析、逐小时天气、记录分别建缓存表 | 与我们的 `climate_profile` 分工一致，缓存表设计可直接照搬 |
| 温度不兼容的单品**仍进候选**，只是退为"兜底候选"并说明 | 这就是 `skip` 态的产品化表达 |
| 推荐结果附逐条理由列表 | 我们 `reason` 拼装的展示形态 |
| 下雨时鞋走防水/防滑加分 | 与第七节第 3 条的降雨规则同构 |

**不能抄的**：它的 `score_item` 全程是字符串包含匹配（`"雨" in condition`、`token in searchable_text`），并且把星座幸运色算进得分。判据是玩具级的。

### 2·补.5 `googlarz/fashion-skill`（19★，"Other"）—— 内容结构的参照

一个 Claude Code Skill，把穿搭知识拆成 16 份 reference：`formulas` / `outfit-builder` / `color-palette` / `feedback` / `seasonal-rotation` / `shopping` / `visualize` 等。三点值得借鉴：

1. **M3 课程的组织方式**：一个模块一份 reference，例句全部落在用户自己的单品上。与我们的"规则 ID = 课程章节 ID"同构，可对照它的颗粒度。
2. **穿搭公式自动发现**：同一核心组合出现 ≥3 次且情绪为 confident/comfortable → 固化成一条命名公式（"Dark Office"、"Earth Easy"）。这对我们是低成本的 M4 功能，且比单纯调权重**可展示、可教学**。
3. **A 视图的版式**：HTML flat-lay，单品按行排 + 连接线 + 右侧"Why it works"侧栏 + 匹配度条。可以直接照这个版式做 M1 的 A 视图。

许可是 "Other"，文字不要复制，只学结构。

## 三、可以直接移植的代码

### 3.1 身体槽位模型与去重（`wardrowbe/backend/app/utils/clothing.py`）

这是整个调研里**最值得抄的一段**。我们的 `layers` 多值数组能表达"衬衫=内层+中层"，但挡不住这些错误组合：

- 两条裤子同时出现；
- 连衣裙 + 裤子；
- 西装外套当内层穿；
- 没穿上衣（只有外套）却当成完整一套。

它的做法：

| 机制 | 作用 |
|---|---|
| `ITEM_ROLE`：品类 → 角色（base_top / mid_layer / outer_layer / bottom / footwear / full_body / suit / accessory） | 32 种品类归到 8 个角色 |
| `ROLE_SLOTS`：连衣裙占 `{base_top, bottom}`，西装占 `{bottom, suit}` | 一件多槽位，天然挡掉"连衣裙配裤子" |
| `deduplicate_by_body_slot()` | 按槽位认领，先多槽位后单槽位；重复的直接丢弃 |
| `covered_regions()` / `missing_regions()` | 判"上半身/下半身/脚"是否都被覆盖；缺口诊断**直接复用** |
| `WORN_ALONE_TYPES` | 连帽衫这类可以单穿的外层，算作上衣 |

**移植建议：** 原样翻译成 Python（本来就是 Python），替换我们 4.1 的枚举逻辑。我们的 `layers` 字段保留，但枚举前先按角色展开成槽位。

### 3.2 规则过滤与渐进退让（`dresser/src/dresser/rules.py`）

| 机制 | 我们的现状 | 建议 |
|---|---|---|
| `target_warmth(t) = clamp(1 + (30-t)/7, 1, 5.5)` 连续目标 | 4 档硬边界 | 档位保留做硬约束，连续目标用于 R-OCC-03 的软评分 |
| **四级放宽**：严格 → ±0.5 → ±1.0 → ±2.0，结果标 `relaxed=True` | 违反硬规则直接丢弃，**可能返回 0 套** | 必须加。三十件衣服配 24 条规则，全灭是现实风险 |
| `_diverse_top()`：新组合与已选组合共享 ≥3 件就跳过 | 无 | 必须加。否则 37 套里 30 套是同一件外套换个内搭 |
| `adjust(pieces)` 钩子：历史只重排、不放行 | 无 | 采纳。轮换不能绕过硬规则 |
| 雨天规则：`suede/canvas` 鞋扣分，`trench/waterproof` 加分 | 无 | 见第七节第 3 条 |

它的硬规则很朴素，只有"厚度目标 ± 容差 + 正式度区间 + 单件厚度上限"，但**结构是对的**：先筛后评，失败逐级放宽，并诚实标注。

### 3.3 穿着轮换（`dresser/src/dresser/rotation.py`）

权重是作者自定的，没调参，但数值可作起点：

| 情况 | 调整 |
|---|---|
| 今天/昨天穿过 | −2.5 / 件 |
| 2–3 天前穿过 | −1.0 / 件 |
| 久未穿 | 最多 +0.5 / 件（21 天满） |
| 刚被"换一套"划过 | 最多 −4，14 天线性衰减到 0 |

只用一条规则就解决了"每天推同一套"。我们记录了 `adopt`，但没有 `last_worn`，这是白丢的信息。

### 3.4 天气（`dresser/src/dresser/weather.py`）

- Open-Meteo `/v1/forecast`，无 key；
- 按**当天最低与最高的中点**选衣，而不是当前温度（早上和中午的穿法不同）；
- 降雨概率 ≥50% 视为下雨；
- 按地点缓存 3 小时，断网时回落到当天缓存并标注。

我们的 `climate_profile` 解决的是"这个地点一年怎么穿"，它解决的是"今天怎么穿"，两者互补，缓存层可以共用一套写法。

### 3.5 属性提取（`dresser/src/dresser/describe.py` + `wardrowbe/backend/app/prompts/clothing_analysis.txt`）

两件事值得直接搬：

1. **受限输出契约。** `clothing_analysis.txt` 把品类、颜色、图案、材质、正式度、风格、季节、版型全部限定在枚举里，并要求输出单个 JSON 对象、不许多余文字。这比"请描述这件衣服"稳定一个量级。
2. **以图片 hash + 模型名做缓存。** 重跑不会重复花钱，也不会因为模型换了而静默复用旧结果。

我们文档里"VLM 预填 + 人工确认"的顺序是对的，见第五节实测数据。

### 3.6 配对学习（`wardrowbe/backend/app/services/learning_service.py`）

它是**配对级**，我们是规则级：

```
每对单品的统计：配对次数、接受次数、拒绝次数、评分总和、穿着次数
兼容分 = (接受率 × 0.6 + 归一化评分 × 0.4) × 2 − 1   → [-1, 1]
样本门槛：MIN_PAIRS_FOR_SCORING（默认 5 次配对）以下一律返回 0
```

配对级比规则级更适合我们的数据量：三十件衣服、每天一次反馈，单条规则要凑满 5 次采纳要很久，但"这件外套配这条裤子"出现得频繁得多。而且它直接服务 V1 的第三项需求——**选中一件 → 配一套**。

### 3.7 商品链接导入（`dresser/src/dresser/linkimport.py`）——V2 直接可用

含完整的 SSRF 防护：只允许 http/https 与 80/443/8080/8443，解析后必须是公网地址，每次重定向重新校验，10s 超时、2MB 页面上限。它还实测了 16 个电商站：Allbirds/Everlane/Uniqlo/Nike 可用，Zara/淘宝/天猫不可用（图在 JS 里）。

这正好回答 V2 的第一个问题：**不要做"贴淘宝链接"，做"贴图"**。

| 天气与气候 | Open-Meteo（Forecast / Archive / Geocoding） | 免费无 key | 与 `dresser`、`wardrowbe` 的实测一致 |
| 浏览器内抠图（可选） | `@imgly/background-removal` 1.7 | **AGPL-3.0** | 只在纯前端方案用；我们是 Python 后端，不需要 |

### 4.1 A4 当比例尺 → 印刷标定卡（已采纳）

`02` 里 A4 方案的问题：白纸边缘在白色背景上不可靠，衣服本身也可能是白的；透视稍歪，误差就超过 ±2cm。

更稳的做法是**印一张 A4 卡，一次性贴在拍摄区**：

- 一个 5cm 的 **ArUco 标记**（`cv2.aruco.DICT_4X4_50`）→ 精确尺度，亚毫米级；
- 一块 18% 灰 + 一块白 → 白平衡与曝光校正；
- 可选 6 个色块 → 校验色彩提取误差。

成本是多一次打印，收益是尺寸、白平衡、色彩三件事一起解决，且算法都是现成的。`02` 已按此改写；**精度仍待实测**（拿一件真实衣服量一遍，误差可接受才进代码）。

### 4.2 颜色规则改用 CIEDE2000（已采纳）

我们现在用裸的明度差（`R-COL-02/03` 的 `<15` / `≥15`）判断"糊成一片"。问题：明度差相同的一对深蓝/深灰和一对米白/浅卡其，人眼感受完全不同。

`colour.difference.delta_E_CIE2000(lab1, lab2)` 是行业标准，一行代码。`02` 已按下面两条改写：

- 硬规则仍用可解释的量（主色数、饱和度），因为课程里要讲得明白；
- 软规则 `R-COL-02/03` 改用 ΔE00，阈值先取 10（明显可辨）与 25（对比强烈），M1 结束按实际观感校准。

这不会改变规则数量，只让 `R-COL-02/03` 的阈值有依据。

## 五、VLM 打标的实测数据

`dresser/docs/vision_eval.md` 在 21 件真实衣服上评了四个模型（单位：准确率）：

| 模型 | 品类 | 类型 | 颜色 | 厚度 ±1 | 正式度 ±1 | 材质 | 中位耗时 |
|---|---|---|---|---|---|---|---|
| Qwen3-VL-8B-Instruct | 81% | 76% | 90% | 67% | 86% | 67% | 3.1s |
| Qwen3-VL-30B-A3B | 90% | 81% | 100% | 100% | 90% | 67% | 4.4s |
| Qwen3-VL-32B | 95% | 71% | 95% | 90% | 86% | 71% | 6.0s |
| GLM-4.5V | 90% | 81% | 95% | 90% | 86% | 67% | 9.2s |

样本只有 21 件、一个人，**只能当方向看**，但足以得出三条判断：

1. **颜色可信，材质不可信。** 颜色 90–100%，材质四个模型都在 67% 左右。材质若进规则，必须人工选，不能靠模型。
2. **品类/类型 80% 上下。** 也就是说每五件就有一件要改。人工确认不是"保险"，是流程必需。
3. **本机 16GB M1 的现实档位**：8B 的 4-bit 约 5GB，能跑；30B-A3B 的 4-bit 约 17GB，跑不了。若坚持本地打标，用 8B，同时接受品类 81% 的准确率，并依赖确认步骤兜底。

> 若走云端 VLM，会与项目红线"不把衣柜照片上传第三方（除非明确同意）"冲突。**默认必须是本地模型或纯手工录入**，云端作为显式选项。

## 六、明确不用的东西

| 东西 | 为什么不用 |
|---|---|
| Polyvore / Outfit Transformer 等兼容性模型 | 需要数据集训练，输出是向量相似度，**解释不出一句人话**，与"reason 不调模型"直接冲突 |
| CLIP / DINOv2 风格嵌入 | 同上。能找"相似"，不能判"成立" |
| LLM 直接生成搭配（wardrowbe、ai-closet 的做法） | 不可复现、无法单测，同一输入两次结果不同 |
| Libre-Closet 的代码 | AGPL-3.0，只能看交互，不能抄 |
| 生成式 VTON 进 M1 | 它美化旧衣（`02` 的红线），只属于 M4 的 C 档 |
| 从照片自动测身体尺寸 | 相关仓库（`farazBhatti/Human-Body-Measurements-using-Computer-Vision` 等）都依赖参考物与站姿假设，误差不可控；手量 9 项更靠谱 |

> M4 的 C 档如果自托管，注意 OOTDiffusion / IDM-VTON / CatVTON 都是**研究用自定义许可（多为非商业）**。个人自用没问题，任何对外发布前必须重新核查许可。
