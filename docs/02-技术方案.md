## 一、架构总览

```
手机浏览器（PWA）
  │  拍照直传 / 组合浏览 / 反馈
  ↓
FastAPI
  ├── extract/    属性提取：M1 人工录入；标定校正与 VLM 预填留到 M2+
  ├── rules/      规则引擎：纯函数，无 IO
  ├── render/     三视图渲染：A 平铺 / B 合成 / C 调 API
  └── SQLite      单品库 / 身材 / 组合 / 反馈
```

**技术栈选择**

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | Python + FastAPI | M2 的图像处理（抠图、关键点、形变）生态在 Python |
| 规则引擎 | 纯 Python 函数 | 无 IO，可单测，可被课程复用 |
| 前端 | React + Vite + PWA | 手机可拍照直传、可加到主屏、可调系统分享面板 |
| 数据库 | SQLite | 单人使用，几十到几百件，不需要服务型数据库 |
| 气候 | Open-Meteo（Geocoding + Archive + Forecast） | 免费、无需 API key；一次算完永久缓存 |
| 图像 | OpenCV / rembg / MediaPipe | M2 用；M1 不需要 |
| 色差 | colour-science 0.4.7 | CIEDE2000 一行调用，用于软色彩规则 |

## 二、单品属性 schema

> **这是整个项目最重要的东西。字段错了，后面所有逻辑都建在噪声上。**

### 表 `item`

| 字段 | 类型 | 取值 | 说明 |
|---|---|---|---|
| `id` | INTEGER PK | — | — |
| `name` | TEXT | 自由 | 我自己认得的名字，如"深蓝牛仔外套" |

| `sleeve_cm` | REAL NULL | 肩缝到袖口 | 外套必填；上衣选填（缺失时只跳过袖长判断） |
| `shoe_size` | REAL NULL | 欧码 EU（例 42） | 鞋必填（`confirmed`）；**M1 只存档，不参与任何规则** |
| `waist_cm` | REAL NULL | 平铺腰围（×2 得围度） | 裤子必填 |
| `hip_cm` | REAL NULL | 平铺臀围（腰头下 7–10cm 最宽处，×2 得围度） | 裤子必填 |
| `leg_opening_cm` | REAL NULL | 单腿裤脚的平铺宽（×2 得脚口围） | 裤子必填 |
| `seasons` | TEXT[] | summer/spring_fall/winter | 多值。**仅用于展示分组，不再作为求解硬约束** |
| `status` | TEXT | draft/confirmed/archived | `draft` 与 `archived` 不参与求解；`archived` 照片保留、不从磁盘删除 |
| `source` | TEXT | vlm/manual | 属性来源，用于统计 VLM 准确率 |
| `last_worn_at` | DATE NULL | — | 最近一次穿着日期，**每日建议的轮换依据** |
| `created_at` | DATETIME | — | — |

**关键约束**

1. `layers` 和 `seasons` 必须是多值数组。大多数同类产品在这里出错。
2. `status=draft` 的单品**不参与组合求解**。宁可少几件，也不要用错数据。
3. `color_hex` 人工取色（预设 / 系统调色板 / 照片点选）；M1 不做色卡校正，也不自动提主色。
4. **尺寸分级量取**：外套 4 项（衣长/肩宽/胸宽/袖长）、裤子 4 项（裤长/平铺腰围/平铺臀围/裤口宽）全部必填；上衣（T恤/衬衫/卫衣/毛衣/针织）量衣长、肩宽、胸宽（必填）与袖长（选填）；鞋填欧码（必填，只存档）。衣长、肩宽、胸宽是 `R-SIZ-01` 与长度类规则的主维度，缺一项整套就少一条身形理由；袖长只判长袖，短袖不量也不影响，故选填。此前曾把毛衣/针织排除在尺寸录入之外，现统一按上衣口径处理——它们和 T恤 在求解里是同一个内层槽位，口径不一致会让同槽单品的理由条数不对等。
5. `length_cm` 缺失时，长度类规则（R-LYR-02、R-PRP-04）对该组合**跳过而非判负**——不扣分也不加分。
6. 存储侧：`layers` / `seasons` 以 JSON 数组文本存（SQLite `json_valid` 校验），仓储层与 tuple 互转；色彩派生列（`hue_family` / `lightness` / `saturation` / `warmth`）在写库时由 `color_hex` 算出，只用于查询与展示——规则判定始终只认 `color_hex`，避免出现第二套口径。

|---|---|---|
| `id` | INTEGER PK | — |
| `name` | TEXT | 如"深圳" |
| `lat` / `lon` | REAL | 经纬度 |

### 表 `climate_profile`（全年温度曲线，按地点缓存）

| 字段 | 类型 | 说明 |
|---|---|---|
| `location_id` | INTEGER FK | — |
| `month` / `day` | INTEGER | 一年中的某一天 |
| `temp_avg` | REAL | 近 10 年该日平均体感温度（缺失退平均气温） |
| `fetched_at` | DATETIME | 缓存时间 |

**一个地点只算一次，永久缓存。** 换地点才重算。
**缺失值不填 0：** 某年某日为 null 就跳过，按实际有值的年份求均值；2/29 有几条算几条。

数据源：Open-Meteo Geocoding（地址 → 经纬度）+ Open-Meteo Archive（ERA5 近 10 年逐日数据）。均免费、无需 API key。当天温度取 Open-Meteo Forecast，或手动填入。气候窗口固定为 `today.year-10` 至 `today.year-1`，一次请求拉完整区间。

### 温度区间（替代"季节"作为硬约束）

**取 Open-Meteo 的体感温度 `apparent_temperature`，不是气温。** 同样 12°C，有风与无风是两种穿法；气温不含风速和湿度。

| 体感温度 | 可穿厚度（上装） | 层级要求 |
|---|---|---|
| ≥26°C | thin | 只内层 + 下装，禁止中层与外层 |
| 18–26°C | thin / medium | 单层，或薄外套 |
| 10–18°C | thin / medium | 需中层或外套 |
| <10°C | 中层、外层 medium / thick；内层不限 | 需要中层 + 外层 |

> **R-OCC-01 只检查上装三层（内层 / 中层 / 外层），下装与鞋不参与厚度判定。** 否则 15°C 穿牛仔裤也会被误判违规。`<10°C` 不限制内层厚度：厚毛衣当内搭在冬天是正常穿法，只要求中层与外层够厚。

**档位只做硬约束（R-OCC-01），连续目标做软评分（R-OCC-03）。** 只有档位会出现"25.9°C 与 26.1°C 得到完全不同结果"的断层，只有连续值又无法表达"26°C 不能穿厚外套"。两者并用：

```
target_warmth(t) = clamp(1 + (30 - t) / 7, 1, 5.5)   # t = 体感温度
厚度映射 = thin 1 / medium 3 / thick 5
组合厚度均值 = 上装三层 + 下装的平均值（不含鞋）
偏差 = |组合厚度均值 − target_warmth|            # 越小越好
```

公式来自 `dresser/rules.py`，是经验拟合，不是物理公式；数值可在 M1 结束时按实际观感校准。

`seasons` 字段保留，仅用于分组展示，**不再是求解硬约束**。降水：当前 WMO 天气码属于雨/雪/阵雨/雷雨时 `is_rainy = true`，只影响软规则，不影响枚举（见下节）。

### 天气接入与降级（`src/api/weather.py`）

服务端独占 Open-Meteo 访问，前端只调 `/api/weather`；规则层继续只吃 `Context`，不感知网络。

| 端点 | 用途 | 取值 |
|---|---|---|
| Geocoding | 地址 → 候选 | `name / admin1 / country / lat / lon` |
| Forecast | 当前天气 | `apparent_temperature`（缺失退 `temperature_2m`）、`weather_code` |
| Archive | 十年气候 | `apparent_temperature_mean`；整段窗口都缺体感时不落库，避免把均温标成体感 |

**降级顺序：** 实时体感 → 近 10 年同日体感均值 → 22°C。`source` 取 `forecast / climate / none`；`is_apparent` 标明实时用的是体感还是气温。气候曲线只存体感均值，因此 `source=climate` 时恒为 true；Archive 整段缺少体感则本次不写库，返回失败并允许重取。

**缓存：** 实时按 `(lat, lon, 当地日期)` 缓存 15 分钟；负缓存 60 秒；`refresh=1` 绕过。地理编码按查询词缓存 10 分钟。气候落 `climate_profile` 永久缓存，添加地点时同步尝试，失败不影响保存，可手动重取。

**降水：** WMO 码 51–67、71–77、80–82、85–86、95–99 判 `is_rainy=true`（雨、雪、阵雨、雷雨）。离线同期只有温度，不含降水，固定 false。

**接入规则引擎：** `/api/outfits`、`/api/today` 新增 `is_rainy` 查询参数并写入 `Context`；`Context` 从 `profile` 读取 `height_cm`、`shoulder_cm`（肩宽）、`chest_cm`（胸围）、`hip_cm`（臀围）、`arm_cm`（臂长），无值则 `None`，同时带上字段来源映射（`body/garment/estimated`）。**体重、腰围、颈围、内长本轮只存储，不进入规则**：腰围受低腰与弹力腰头影响、衣件腰头口径不统一；内长没有对应的衣件内缝字段；颈围没有衣件字段；体重没有可靠的单品规则。

**导出：** `GET /api/export` 用 `sqlite3.Connection.backup` 生成 WAL 一致快照，附 `photos.json` 清单（封面 / 抠图 / 追加照片，相对路径、字节、SHA-256、存在性）与 README；路径必须落在 `pic/` 或 `data/photos/` 内，清单不含照片二进制。

## 三、录入流程

```
拍照留档（手机直传，可选，每件最多 6 张，首图为封面）     ← 照片不参与下面任何一步的计算
  ↓
人工填属性（品类/层级/正式度/版型/颜色/图案/厚度，约 30 秒/件）
  ↓
手量尺寸（外套 4 项、裤子 4 项、上衣衣长+肩宽+胸宽必填+袖长选填、鞋填 EU 鞋码；配饰不量）
  ↓
status = confirmed（属性齐 + 条件尺寸齐），否则 draft
  ↓
入库
```

### 四条强制设计

1. **M1 不接照片测量。** 现有 19 件的衣长已全部量完（上衣 9 件也有），剩下的平铺尺寸逐项手量，全部加起来远不到 10 分钟。为了这点时间，要打印标定卡、固定机位、拍 9 张标定照、维护一套校正代码，还得赌它测不准时不会被发现——负收益。标定方案留在本节末尾，作为 M2+ 的候选，**不进 M1 流程**。
2. **拍摄规范：白墙 + 自然光 + 平铺 + 正上方垂直拍 + 拍全。** 不要挂着拍（垂感假）、不要穿着拍（褶皱多）、不要俯拍（广角畸变）。照片只用于衣库与组合卡展示。
3. **M1 不接 VLM，属性和颜色全部人工填。** 品类、层级、正式度、版型、颜色由我从照片点选/取色。数据是地基，不能赌模型的准确率。
4. **尺寸分级量取。** 外套量 4 项（衣长/肩宽/胸宽/袖长），裤子量 4 项（裤长/平铺腰围/臀围/脚口宽），上衣量 3+1 项（衣长/肩宽/胸宽必填，袖长选填），鞋填 EU 码，配饰不量。平均每件约 4 项，10 分钟内完成。

### 拍摄标定：一张印刷标定卡（M1 不用；比例功能已验证不通过）

原先设想用 A4 白纸兼作色卡和比例尺。问题：白纸边缘在白背景上不可靠，衣服本身也可能是白的；拍摄角度稍歪，误差就超过 ±2cm。

改成**一次性印一张 A4 标定卡**，贴在拍摄区：

| 元素 | 作用 | 技术 |
|---|---|---|
| 5cm **ArUco 标记**（`DICT_4X4_50`） | 尺度基准，同时给出透视变换的四个角点 | `cv2.aruco`，OpenCV contrib 自带 |
| 18% 灰块 + 白块 | 白平衡与曝光校正 | 灰度世界 / 白块增益 |
| 6 个色块（RGB 三原色 + 肤色 + 深灰 + 浅灰） | 校验色彩提取误差 | 与 `color_hex` 比对 |

一张卡本来想同时解决尺寸、白平衡、色彩校验三件事，成本只是多一次打印。**尺寸这一件没成，白平衡与色彩校验也没验成，原因都见下。**

> **打印比例的处理（2026-10-26 补）**：卡上的 50mm / 100mm 是**名义尺寸**。
> 打印店若无法设 100%，不要求重印；以卡上 100mm 尺的实测长度 `L` 作为该张卡的比例基准：
> `card_scale = L / 100`，ArUco 真实边长 = `50 × card_scale`。
> 前提是横竖等比——量 18% 灰块横、纵两边，差值 ≤0.5mm 才可用；否则该张作废。
> 这样标定结果不依赖打印机设置，只依赖一次精确测量。

| 尺寸 | 能否由照片估算 | 实测结论（2026-10-26，9 张标定照） |
|---|---|---|
| 衣长 | 只有正拍勉强，偏角不可用 | 误差 0° +0.95 / +1.80cm；15° +4.4 / +7.2cm；30° +9.4 / +13.4cm |
| 裤长 | 无法由平铺轮廓推出 | 裤长定义是**沿侧缝量弧线**；平铺轮廓的纵向跨度比它长 8cm，腰头角→裤脚角的直线又比它短 10cm。0° 误差 +8.0cm |
| 肩宽 / 胸宽 / 袖长 | 精度不足 | 仍需手量 |

**状态：验证不通过（2026-10-26）。M1 全部手量，照片不参与尺寸估算。**

证据：`scripts/spike/gate1_result.json`；分析见 `07-开工前检查.md` 第五节。三条根因：

1. **尺度基准太短。** ArUco 真实边长只有 48.5mm，在画面里占 37–59px。±1px 的角点误差就是 1.7%–2.7% 的尺度误差，而衣物离标记 20–40cm，误差被整体放大。
2. **仿射纠不了透视。** 用标记四角拟合仿射只能在该标记处精确，离它越远残差越大。偏 15°/30° 时实测误差随 tanθ 增长（衣长 +0.95→+4.35→+9.35，比值 1 : 2.1 恰好是 tan15° : tan30°）。改用标记四角拟合**单应**又因近正方形小四边形条件数太差而失稳——4.0 反而少算 9.3cm。
3. **端点定义与轮廓不等价。** 上装真值从后领中点起量，轮廓顶部却是领口上沿（立领夹克差 1–2cm）；裤子的侧缝是弧线，轮廓既量不出弧长也给不出它的两端。

**先读这条经验再决定要不要重做标定卡**：标定卡的已知几何必须占画面的足够比例，否则角点噪声会主导结果。若 M2 之后重启自动估尺寸，v2 卡至少要：A3 或更大、ArUco 边长 ≥100mm、另加一条 ≥200mm 的校准尺、拍摄时卡与衣物的间距 ≤15cm，并且**只允许正拍**。这三条没同时满足，重做一遍仍是同样的结果。

**色彩那一项本轮也没验成**：打印店把卡印成了黑白，六个色块在照片里全是中性灰（`calibration_card_a4.png` 本身是彩色，问题在打印）。要验 ΔE00 得拿同一份 PDF 重印一次彩色的。在此之前 `color_hex` 一律人工从照片取色。

### 一条红线

**永不使用生成式模型重绘单品图。** 那会让衣服变成模型想象的样子，跟我手上那件不是同一件。还原的目标是"像我的那件"，不是"好看"。

## 四、组合求解

### 4.1 先展开槽位，再枚举

**不能直接按 `layers` 多值数组做笛卡尔积。** 那样会产出"两条裤子""连衣裙配裤子""只有外套没有上衣"这类组合，且无法判断"这套是否完整"。

先把每个品类映射到**身体槽位**：

| 角色 | 品类 | 占用的槽位 |
|---|---|---|
| `base_top` | T恤 / 衬衫 / 针织 / 毛衣 / 卫衣 | 上衣 |
| `mid_layer` | 针织 / 卫衣 / 薄夹克 | 中层 |
| `outer_layer` | 外套 / 夹克 / 西装 | 外层 |
| `bottom` | 裤子 / 牛仔裤 / 短裤 | 下装 |
| `shoes` | 鞋 | 鞋 |
| `accessory` | 帽子 / 围巾 / 包 / 腰带 | 配饰（可选） |
| `full_body` | 连体装 | 上衣 + 下装（一件占两槽） |
| `suit` | 西装套装 | 外层 + 下装（一件占两槽） |

枚举时套用三条约束：

1. **每个槽位至多一件。** 多槽位单品先认领，占用后该槽位不可再放。
2. **必须覆盖 上衣 + 下装 + 鞋。** 缺任一不算完整套，不进入候选。
3. **外层与中层可空**，内层不可空（`full_body` 除外）。

以 8 件内层、5 件下装、3 双鞋、2 件中层、2 件外层计：

```
8 × 5 × 3 × 3 × 3 = 1080
```

**一千量级的组合，暴力枚举 + 规则评分完全够用。不需要任何搜索算法、向量检索或图算法。** 这是 M1 工作量小的根本原因。

> 槽位模型来自 `Anyesh/wardrowbe` 的 `utils/clothing.py`（MIT），已核实可用。

### 4.2 锚定求解（选中一件 → 配一套）

这是 V1 第三项需求，必须是一等公民，不能靠"全量枚举后再筛"。

```
固定锚定单品 a
  ↓
只枚举能补全 a 的槽位组合（a 已占的槽位不再枚举同类）
  ↓
与全量求解共用同一批规则、同一套权重
  ↓
先按放宽档位、同档按总分排序，取前 N 套
```

两种模式的区别只在枚举范围，**规则与评分的代码路径必须完全相同**——否则"选一件配一套"和"看全部组合"会给出互相矛盾的答案。

### 4.3 两阶段评分

```
枚举全部组合（槽位合法）
  ↓
① 硬规则过滤（违反任何一条 → 丢弃）
  ↓
② 软规则加权求和（得分 = Σ 规则权重 × 命中值）
  ↓
③ 按场合 / 温度区间分组输出
  ↓
④ 排序：先按放宽档位升序，同档再按得分降序
```

**顺序不能反。** 先过滤再评分，才能保证输出的每一套都是"至少不违规"的。

**排序也不能只看得分。** 放宽 2 档的组合可能因命中更多软规则而得到比严格档更高的分（干跑实测 8.0 vs 7.0）。档位必须排在得分之前，否则界面上会出现"放宽的组合排在全合规组合前面"。

### 4.4 渐进放宽（硬过滤可能全灭）

三十件衣服配二十几条规则，硬规则全灭不是理论风险：`loom` 的实测里，纯多模态方案因为硬门槛少了 12% 的完整套。

| 档位 | 做法 | 处理 |
|---|---|---|
| 0 | 全部硬规则 | 正常输出 |
| 1 | 容差 ±0.5（厚度、正式度、鞋差） | 标记 `relaxed=1`，每条扣 1 分 |
| 2 | 容差 ±1.0 | 标记 `relaxed=2`，每条扣 2 分 |
| 3 | 容差 ±2.0 | 标记 `relaxed=3`，每条扣 4 分 |

> **厚度的容差口径：** R-LYR-01 已允许同厚，因此档位 1（±0.5）与档位 2（±1.0）对厚度不产生额外放宽；只有档位 3（±2.0）允许外层比相邻内层薄一档。正式度与鞋差仍按 ±0.5 / ±1.0 / ±2.0 连续放宽。

规则：

- **槽位约束永不放宽**（放宽后就不是一套衣服了）。
- 只有"程度类"硬规则可放宽（R-LYR-01 厚度、R-FRM-01/02 正式度、R-SHO-01 鞋差、R-OCC-01 温度兼容）；"关系类"硬规则不放宽（R-COL-01 主色数、R-PRP-01/02 双宽双紧、R-PAT-01 大图案）。
- 放宽后的结果必须在界面上明确标注：**"没有完全合规的搭配，以下为放宽 X 档后的结果"**。诚实标注比悄悄降级重要。

### 4.5 多样性去重

1080 个组合里，前 37 名很可能共享同一件外套，只是换内搭和裤子。

```
先按放宽档位、同档按得分从高到低遍历
  新组合与任何已选组合共享 ≥3 件 → 跳过
  否则收入结果，直到凑满 N 套或遍历完
```

N 默认 10（界面显示 5 套 + 展开更多）。**这是"看起来有 37 套"和"真的有 37 种穿法"的区别。**

### 4.6 输出结构

每条组合返回（`items` 为摊平后的单品，`explanation` 见 4.8）：

```json
{
  "hash": "8f3c…",
  "score": 7.5,
  "level": 0,
  "relaxed_rules": [],
  "reason": "上装合身：…；下装合身：…；藏青外套与浅灰内层 ΔE00 = 42，层次清楚",
  "thumbs_up": ["R-COL-03", "R-PRP-03"],
  "thumbs_down": [],
  "items": [{"id": 12, "slot": "base_top", "slot_label": "内搭"}],
  "explanation": {
    "headline": "16°C 日常：上窄下宽，同色系深浅分层。",
    "principles": [{"principle_id": "P-VIS-01", "rule_id": "R-PRP-03"}],
    "caveats": [],
    "style": {"label": "日常 · 上窄下宽 · 中性色主导", "inferred": true},
    "data_gaps": [],
    "version": "explain-v1"
  }
}
```

`reason` 由命中的软规则自动拼装，**不调大模型**——M1 阶段要保持可复现。最多 5 条，`siz` 的两条身形理由排在最前。色彩关系的描述可用六类色彩关系（同类 / 邻近 / 互补 / 三角 / 分裂互补 / 中性）作为措辞，但**不为它新增规则**，只影响文案。

`reason` 保留为**兼容字段**：旧测试、旧反馈归因和前端回退仍可使用，本轮不改变其拼装逻辑与文案。面向用户的「为什么」由新增的 `explanation` 承担（4.8），它不再是一条扁平字符串，而是结论 + 原理行 + 注意事项 + 风格推断 + 数据缺口的结构化对象。

### 4.7 每日建议的轮换

规则分数一样的组合，天气不变时会每天推同一套。在排序最后叠加轮换修正（不改变合规性，只改顺序）：

| 情况 | 修正 |
|---|---|
| 今天或昨天穿过 | −2.5 / 件 |
| 2–3 天前穿过 | −1.0 / 件 |
| 久未穿 | 最多 +0.5 / 件（21 天到顶） |
| 最近被"换一套"划过 | 最多 −4，14 天线性衰减到 0 |

数据来自 `item.last_worn_at` 与 `feedback`。**轮换只重排，永不放行被硬规则拒绝的组合。**

**记录每天展示了什么。** 当日建议写入 `daily_suggestion`（`day` 主键 / `outfit_hash` / `garment_ids` / `hit_rules`），一天一行，点「再换」时覆盖为新的组合。次日首次生成建议时，逐行检查该 hash 当天有没有任何反馈（含 adopt / swap / favorite / veto_item / ignore）：没有就补记一条 `ignore`，携带当时展示的 `garment_ids` 与 `hit_rules`；处理完删除该行。这张表只记录展示事实，不参与求解排序。

| 字段 | 类型 | 说明 |
|---|---|---|
| `day` | TEXT PK | 本地日期 `YYYY-MM-DD` |
| `outfit_hash` | TEXT | 当天最后展示的组合 |
| `garment_ids` | INTEGER[] | 补记 `ignore` 时要用 |
| `hit_rules` | TEXT[] | 当时的软规则命中，用于归因 |
| `created_at` | DATETIME | — |

### 4.8 解释层

`reason` 回答「哪条规则加了分」，`explanation` 回答「这套为什么成立、依据是什么、下次怎么自己看」。两者并存，职责不同。

```
solve() / assess()                 规则引擎，保持原样
   ↓ Assessment(candidate, level, score, soft_hits, relaxed_rules, reason)
API 序列化 _outfit_out(assessment, ctx)
   ↓ 只对最终返回的 1–10 套调用
explain(assessment, ctx)           纯函数：把规则命中翻译成有依据的解释
   ↓ Explanation(headline, principles, caveats, style, data_gaps)
OutfitOut.reason（保留）+ OutfitOut.explanation（新增）
```

**硬边界**

- **不进入求解热路径。** `solve()` 会对上千个候选调用 `assess()`；解释只对最终返回集生成，放在 `_outfits_response` 里。有测试 monkeypatch `explain` 为抛异常函数，锁住「`solve()` 不调用解释」。
- **不二次判断。** `explain()` 只读 `soft_hits`、`relaxed_rules`、`candidate`、`ctx`；阈值从规则模块 import，不复制第二套口径；不重算分数、不改等级、不改排序、不放宽阈值。
- **不调模型。** 与 `reason` 一样保持确定性、可复现，不生成图片。
- **不加 schema。** 不新增 `style_tags`、次要色、风格原型字段；缺数据写「未参与」。
- **负向不进正向。** `value < 0` 的软命中、放宽规则、上下文偏差只进 `caveats`；`is_scored` 为假不生成原理行；硬规则 PASS 不直接复述空泛套话。

**结构**

| 字段 | 内容 | 约束 |
|---|---|---|
| `headline` | 体感温度 + 场合 + 2–3 个已选原理短语 | 不复述规则 ID，不重复 `reason` |
| `principles` | 原理行：`principle_id / rule_id / title / evidence / why / how_to_judge / grade / source` | 1–5 条；有证据时 2–5 条；同一 `axis` 最多 2 条；预留 1 条给 SIZ |
| `caveats` | 放宽 / 负向扣分 / 上下文偏差 | ≤3 条；`severity` 为 `info` 或 `warn` |
| `style` | 场合 + 轮廓 + 色彩倾向 + 推断依据 | `inferred=true`；只描述，不计分 |
| `data_gaps` | 真正影响本套判断的缺项 | ≤2 条；不写泛泛的「数据不足」 |
| `version` | 解释结构版本 | M1 固定 `explain-v1` |

**选择顺序**：先取 `is_scored and value > 0` 的软命中，按 `R-* → P-*` 映射去重；展示顺序为 `视觉 → 色彩 → 合身 → 层次 → 社会 → 材质 → 图案`；正向行不足 2 条时，最多补 1 条「结构底线」。

**理论库**：`docs/11-搭配理论库.md` 定义 18 条原理、A/B/C/D 依据分级与五种状态；`src/rules/theory.py` 是同一份内容的代码化，导入时断言 26 条规则全部被覆盖、P-ID 唯一、`dormant` 不进入正向行。App 的 `/theory` 页只读展示同一份 `PRINCIPLES`，做到「文档、代码、界面」三处同源。

**映射关系**（完整表见 `docs/11` 第 0.4 节）：

| 轴 | 原理 | 规则 |
|---|---|---|
| 视觉 | P-VIS-01/02 | R-PRP-01/02/03/04 |
| 色彩 | P-COL-01~06 | R-COL-01~06、R-SHO-02 |
| 合身 | P-FIT-01/02 | R-SIZ-01/02 |
| 层次 | P-LAY-01/02/03 | R-LYR-01/02/03 |
| 社会 | P-SOC-01/02/03 | R-FRM-01/02、R-OCC-01/02/03、R-SHO-01/03 |
| 材质 | P-TEX-01 | R-MAT-01 |
| 图案 | P-PAT-01 | R-PAT-01/02 |

**性能**：单套解释是 O(单品数) 的常量级工作，目标 <1ms；10 套新增 <10ms，相对最慢 0.46s 的求解可忽略。微基准 100 次 <0.5s 作为宽松回归线。

**接口**：`GET /api/theory` 返回按轴分组的 18 条原理与「数据不足」清单；静态内容，进程内只构建一次，不读数据库。

## 五、规则表

> 每条规则的 ID 同时是课程章节的 ID。**写不出教学解释的规则，删掉。**

**规则的返回值是三态，不是布尔：`pass` / `skip` / `fail`。** `skip` 表示该组合缺少判断所需的数据（如无 `length_cm`），既不扣分也不加分。硬规则遇到 `skip` 时按 `pass` 处理，软规则遇到 `skip` 时该项不参与加权。缺这一态就会把"数据没有"错判成"搭配不对"。

### 合身（SIZ）

两条规则都是软规则，**只扣分/加分，不做硬排除**。身材来源可能含估算值、衣件尺寸也常缺，硬过滤会把"没量"误判成"不能穿"。状态一律 `PASS` + 有符号分值（负值即扣分），不使用 `FAIL`——`is_scored` 只认 `PASS` 且 `value != 0`，写 `FAIL` 会让理由与 `thumbs_down` 一起消失。

| ID | 类型 | 规则 | 分值范围 |
|---|---|---|---|
| R-SIZ-01 | 软 | 上装合身：肩线、胸围松量、袖长（`base_top` / `mid_layer` / `outer_layer` 逐件判，按维度取最差一件） | −2.5 ~ +0.2 |
| R-SIZ-02 | 软 | 下装合身：臀围松量（只看 `bottom`） | −1.0 ~ +0.2 |

**判定口径**

| 判定 | 衣件字段 | 身体字段 | 比较 |
|---|---|---|---|
| 肩线 | `shoulder_cm` | `shoulder_width` | 直接相减：`d < −2.5` 扣 1.0（会绷）；`−2.5~2.5` 合身；`2.5~7` 中性；`>7` 且非 oversize 扣 0.5（落肩过头） |
| 胸围松量 | `chest_width_cm × 2` | `chest` | `e = 衣件胸围 − 身体胸围`，按槽位 × 版型的区间判：低于下界 1cm 以上扣 1.0（偏紧），高于上界 1cm 以上扣 0.5（偏松） |
| 袖长 | `sleeve_cm`（≥40 才判，短袖跳过） | `arm_length` | `s = 衣件袖长 − 臂长`：`<0` 或 `>8` 扣 0.5，`0~8` 合身 |
| 臀围松量 | `hip_cm × 2` | `hip` | `e < 0` 扣 1.0（坐下会绷）；`0~2` +0.1（贴体）；`2~10` +0.2（合适）；`>10` 扣 0.3（偏肥） |

胸围松量区间：

| 槽位 | slim | regular | oversize |
|---|---|---|---|
| base_top | 0–8 | 4–12 | 10–24 |
| mid_layer | 2–10 | 6–16 | 12–26 |
| outer_layer | 6–14 | 8–20 | 14–30 |

**聚合与理由**

- 三个维度各自取加权后最负的一件，再相加（不跨件累加），下限 −2.5。正常叠穿不会被叠成重罚。
- 同一件占多个槽位只评一次，按最外层槽位取胸围区间；连体装分别由 `R-SIZ-01`（按 `base_top`）与 `R-SIZ-02`（按臀围）各判一次，不是重复扣分。
- 全部合身 → `+0.2 × min(实际评过的维度权重)`；来源权重 `body 1.0 / garment 0.85 / estimated 0.5`，估算/量衣在理由末尾标注。衣件的 `source`（manual/vlm）是录入方式，不参与权重。
- 任一侧数据缺失 → 该维度 SKIP，不扣分；一条规则一个维度都评不上 → 整条 SKIP。
- 理由上限 5 条，`siz` 在软规则顺序最前，两条身形理由先占位；每条复合规则只产出一条理由，内部不用 `；`（卡片按 `；` 切行）。
- `/gaps` 只统计硬规则可行性，不计算 SIZ；它自建的 `Context` 不带身体字段，两条 SIZ 规则自然 SKIP。

### 色彩（COL）

| ID | 类型 | 规则 | 先验权重 |
|---|---|---|---|
| R-COL-01 | 硬 | 全身主色数量 ≤ 3 | — |
| R-COL-02 | 软 | 相邻层 **ΔE00 < 10** 且不同色系 → 扣分（"糊成一片"） | −2 |
| R-COL-03 | 软 | 同色系且 **ΔE00 ≥ 10** → 加分（深浅叠穿） | +2 |
| R-COL-04 | 硬 | 高饱和冷色 + 高饱和暖色同时出现 → 丢弃 | — |
| R-COL-05 | 软 | 全身饱和度总和 >200 → 扣分（都在抢眼） | −1.5 |
| R-COL-06 | 软 | 至少一件中性色（白/灰/黑/藏青/卡其/米）打底 → 加分 | +1.5 |

> **软色彩规则用 CIEDE2000（ΔE00），不用裸明度差。** 明度差相同的一对深蓝/深灰和米白/浅卡其，人眼感受完全不同。硬规则（R-COL-01/04）仍用主色数和饱和度，因为这两个量在课程里讲得明白。阈值 10 = 明显可辨，25 = 对比强烈；M1 结束时按实际观感校准。实现在 `colour.difference.delta_E_CIE2000`。

**色彩实现口径（M1 固定，干跑已验证）**

| 判定 | 口径 |
|---|---|
| 主色（R-COL-01） | 饱和度 ≥15 且非中性色，按色系去重后计数；低饱和色不算“主色” |
| 高饱和（R-COL-04） | 饱和度 ≥60 |
| 中性色 | 黑/白/灰：S<12 或 L<10 或 L>92；藏青：195–245°、L≤38、S≤70；卡其/米：20–60°、S≤50、L 55–88 |
| 色系 | 红 <15° / ≥345°，橙 15–45°，黄 45–70°，绿 70–165°，青 165–195°，蓝 195–255°，紫 255–345° |

### 正式度（FRM）

| ID | 类型 | 规则 | 先验权重 |
|---|---|---|---|
| R-FRM-01 | 硬 | 相邻层正式度差 ≤ 1 | — |
| R-FRM-02 | 硬 | 全身正式度极差 ≤ 2 | — |

正式度锚点：运动 1 / 休闲 2 / 日常 3 / 商务休闲 4 / 正装 5。

> **"是否匹配场合"只由 R-OCC-02 判定**（见 OCC 模块）。FRM 只管内部一致性与跨度，不再重复定义场合目标值。

### 比例与轮廓（PRP）

| ID | 类型 | 规则 | 先验权重 |
|---|---|---|---|
| R-PRP-01 | 硬 | 禁止上 oversize + 下宽松（双宽会垮） | — |
| R-PRP-02 | 硬 | 禁止上 slim + 下 slim（双紧局促） | — |
| R-PRP-03 | 软 | 上宽下窄 或 上窄下宽 → 加分 | +2 |
| R-PRP-04 | 软 | 身高 <170 时，外套下摆落在小腿中段 → 扣分（需 `length_cm` + `height`，缺失则跳过） | −1 |

### 层次（LYR）

| ID | 类型 | 规则 | 先验权重 |
|---|---|---|---|
| R-LYR-01 | 硬 | 厚度必须 **外层 ≥ 中层 ≥ 内层**（允许同厚，禁止外层比内层薄） | — |
| R-LYR-02 | 软 | 三层时相邻长度差 ≥ 5cm → 加分（依赖 `length_cm`，缺失则跳过） | +1.5 |
| R-LYR-03 | 软 | 两层领型重复（如双高领）→ 扣分 | −1.5 |

### 材质（MAT）

| ID | 类型 | 规则 | 先验权重 |
|---|---|---|---|
| R-MAT-01 | 软 | 相邻层材质有对比（外层挺括/粗糙，内层平滑/柔软）→ 加分（需 `material`，缺失则跳过） | +1.5 |

> 材质是 VLM 最不可靠的字段（实测四个模型都在 67% 左右），因此 `material` 缺失是常态，这条规则大部分时候会返回 `skip`——这是设计好的，不是失败。

> 温度相关的硬约束统一归 OCC 模块（R-OCC-01），材质模块不再重复定义，避免同一件事两处判断出现分歧。

### 图案（PAT）

| ID | 类型 | 规则 | 先验权重 |
|---|---|---|---|
| R-PAT-01 | 硬 | 全身 `pattern=bold` 最多一件 | — |
| R-PAT-02 | 软 | 图案件处于视觉主体位置（外层/下装）且其余全纯色 → 加分 | +1 |

### 鞋与配饰（SHO）

| ID | 类型 | 规则 | 先验权重 |
|---|---|---|---|
| R-SHO-01 | 硬 | 鞋的正式度与全身均值差 ≤ 1 | — |
| R-SHO-02 | 软 | 鞋与上装或配饰同色系 → 加分 | +1.5 |
| R-SHO-03 | 软 | 降水（`is_rainy`）时，麂皮/帆布/缎面鞋扣分；防水/皮靴加分（需 `material`，缺失则跳过） | −1.5 / +1 |

> 鞋是整套的定调器，这是男性穿搭里最容易被忽略的一条。

> 规则的输入是"单品集合 + 上下文（场合 / 体感温度 / 是否降水）"，仍然是纯函数——上下文由调用方传入，规则自己不去查天气。

### 场合与温度（OCC）

场合取值（V1 只有三个）：`日常` / `旅游` / `见人`。

| ID | 类型 | 规则 | 先验权重 |
|---|---|---|---|
| R-OCC-01 | 硬 | **上装厚度与当前温度区间兼容**（区间见第二节表格；只查内层/中层/外层，不查下装与鞋） | — |
| R-OCC-02 | 软 | 场合 → 目标正式度区间：日常 2–3 / 旅游 2–3（加权舒适耐走）/ 见人 4 | +2 |
| R-OCC-03 | 软 | 温度与厚度完全匹配（落在区间中部而非边缘）→ 加分 | +1.5 |

> **季节不再作为硬约束。** 原因是季节标签模糊（"10 月底算秋还是冬"），而温度可计算、可直接对应衣服厚度。`seasons` 仅用于展示分组。

> **体感温度缺失时**（用户没填、也没取到天气），R-OCC-01 与 R-OCC-03 返回 `skip`，不判失败——避免把"没有天气数据"错判成"这套不能穿"。

> 先验权重都是**初始值**，M4 起由采纳数据微调。调整门槛：单条规则 ≥5 次采纳记录。

## 六、三视图

同一份组合数据，三种渲染方式。前端提供切换。

| 视图 | 技术 | 产出 | 判断什么 | 阶段 | 真实度 |
|---|---|---|---|---|---|
| **A 平铺** | 单品图横排 | 一张拼图 | 色彩关系、比例、重心 | M1 | 真实 |
| **B 合成** | 抠图 + 人体关键点 + 分层形变 | 我的衣服贴在我的身上 | 版型、垂感、整体 | M2 | 真实，像拼贴 |
| **C 生成** | VTON API（整套） | 照片级效果图 | "像不像我" | M4 | 像照片，但**美化** |

### 为什么判断层必须是 A/B，不能是 C

生成式试穿会用商品图的先验去"修正"我的衣服：旧 T 恤被画得挺括，褪色的蓝被画饱和。**基于一张美化过的图做判断，等于被骗。**

所以：**C 只用于确认和分享，不参与判断。** 分享需要好看的图，判断需要真实的图——正好是两种技术。

### B 档的技术路径（M2）

1. 基准照 → MediaPipe Pose 取人体关键点
2. 单品图 → rembg 抠图（白背景可直接阈值分割，更稳更快）
3. 按层级顺序，逐件形变对齐到人体（仿射 + 分段网格，非物理模拟）
4. 按 z-order 叠加：内层 → 下装 → 中层 → 外层 → 鞋

**不做物理布料模拟。** 那个成本高一个数量级，而 B 档的目标只是"能判断"，不是"照片级"。

## 七、反馈机制

### 7.1 信号分级（隐性为主）

| 信号 | 我的动作 | 含义 | 权重 |
|---|---|---|---|
| `adopt` | 点"今天穿这套" | 强正 | +2 |
| `favorite` | 标"这套好" | 强正 | +2 |
| `swap` | 点"再换" | 对被换掉的组合中负 | −1 |
| `veto_item` | 在某套里划掉一件 | **最强负，精确到单品** | −2 |
| `ignore` | 没点，关掉 | 弱负 | −0.3 |

**主力信号是 `adopt`。** 如果要求我主动评分，收集率趋近于零。

### 7.2 表 `feedback`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | — |
| `outfit_hash` | TEXT | 组合的唯一键（garment_ids 排序后哈希） |
| `signal` | TEXT | 见上表 |
| `garment_id` | INTEGER NULL | `veto_item` 时填 |
| `hit_rules` | TEXT[] | 该组合命中的软规则，用于归因 |
| `created_at` | DATETIME | — |

`outfit_hash` 口径：`sha1(",".join(升序 garment_ids))` 取前 16 位十六进制。**只要单品集合相同，hash 就相同**，与该组合被哪条锚定路径枚举出来无关。

### 7.3 学什么

| 层级 | 学什么 | 用在 |
|---|---|---|
| **配对级（主力）** | "这件外套配这条裤子"的接受率 | 锚定求解的候选排序 |
| 单品级 | 这件衣服出场时被采纳/否决的比率 → 适配分 | 排序时给单品加权 |
| 规则级 | 哪条软规则的命中组合采纳率高 → 规则权重 | M4 起微调 |

**配对级优先，因为数据密度完全不同。** 三十件衣服每天一次反馈，单条规则凑 5 次要很久；"外套 A 配裤子 B"出现得频繁得多，而且它直接服务"选中一件 → 配一套"。

```
每对单品统计：paired / accepted / rejected / rating_sum
兼容分 = (接受率 × 0.6 + 归一化评分 × 0.4) × 2 − 1     → [-1, 1]
样本门槛：配对次数 < 5 时返回 0，不参与排序
```

公式来自 `Anyesh/wardrowbe` 的 `learning_service.py`（MIT）。表结构：

| 表 `item_pair_stat` | 类型 | 说明 |
|---|---|---|
| `item_a` / `item_b` | INTEGER | 恒满足 `item_a < item_b`，避免重复 |
| `paired` / `accepted` / `rejected` | INTEGER | 计数 |
| `rating_sum` | REAL | 评分累加 |
| `updated_at` | DATETIME | — |

**稀疏数据的硬门槛不变：** 前 30 天基本靠先验规则，不急着学——否则会因为我某天心情不好穿了一件，就以为那条规则错了。

### 7.4 个人标签

单品表加轻量表 `tag`：`dislike` / `love`。**只影响局部，不改规则。** 标签与自动学习并存，但自动学习是主力。

## 九、缺口诊断

独立输出，与组合并列。

```
你的瓶颈：
  外层只有 2 件，且和中层共用同一批黑色夹克 —— 冷天 13 套里有 7 套用它
  下装只有 3 件 —— 凉天 31 套里有 13 套用灰色运动裤

互相配不上的单品：
  （当前没有）

场合适配：
  见人要求正式度 3.5–4.5；当前内层上限 2、中层 3、外层 3、下装 2、鞋 3，最高只有 2.50

若补一条中性色薄直筒裤：
  可组合数 13/31/71/49 → 16/45/96/66（冷/凉/暖/热），合计 +59
```

### 9.1 三条原则

1. **只用真实求解结果，不猜。** 所有数字来自同一次枚举、同一批规则、同一套去重，与 `/outfits` 完全同源。缺口诊断不新增判定规则，只统计已有规则的通过/失败与组合覆盖。
2. **严格档才算成立。** 放宽 1–3 档的组合是「凑合能穿」，不是「这套成立」。用放宽档统计会让缺口全部消失——衣柜永远「有解」。所以有效组合只取 `level == 0`。
3. **不做购物推荐。** 补齐模拟只回答「补哪一类、能多解锁多少套」，不出现品牌、价格、链接与购买按钮。V2 才接商品。

### 9.2 分析口径

**温度带，不是温度点。** `R-OCC-01` 只按区间判定，同一区间内严格档的通过/失败完全一致，所以每带取一个代表值即可，不需要扫温度：

| 键 | 范围 | 代表值 | 上装要求（R-OCC-01） |
|---|---|---|---|
| `cold` | <10°C | 5 | 中层与外层都必须有，且 medium/thick |
| `cool` | 10–18°C | 14 | 中层或外套至少一件，全部 thin/medium |
| `warm` | 18–26°C | 22 | 无中层；外套只能 thin；内层 thin/medium |
| `hot` | ≥26°C | 30 | 只有内层，且 thin |

代表值取带内点，避开 10 / 18 / 26 三个边界——`R-OCC-01` 在边界处阶跃，放宽容差 ±0.5 还会跨带取值，边界上的数字没有解释力。

**场合不影响可解性。** 唯一的场合规则 `R-OCC-02` 是软规则；所有硬规则里没有 `ctx.occasion`。所以每个温度带只求解一次，三个场合共用同一个 `V(b)`，只额外算正式度适配。

**有效组合 `V(b)`：**

```
V(b) = dedup({ 槽位合法的候选 c | assess(c, 日常, b).level == 0 })
```

去重沿用 `MAX_SHARED_ITEMS = 3`，与列表页一致。`V(b)` 是「这个温度带真实成立的、彼此不近似重复的套数」。

**单品归属槽位**按 `placements_of()`：multi-layer 单品（如夹克 `mid+outer`）在两个槽位各计一次，因为它确实能顶两个位置。

**最少件数：** confirmed 单品 < 5 件时不算缺口，直接返回 `insufficient`（`basis.sufficient=false`、`bands` 为空）——少于 5 件，「缺什么」的答案是「缺一切」，没有诊断价值。

### 9.3 温度覆盖缺口

| | |
|---|---|
| 指标 | `\|V(b)\|` |
| 判定 | `< 10` 即缺口；`= 0` 为最高优先级 |
| 严重度 | `(10 - \|V(b)\|) / 10`，clamp [0, 1] |

**为什么是 10：** 10 套是两周不重样。低于 10 套时每日建议会在两周内开始循环，衣柜在这个温度带等于「制服」。0 套则直接说明这个温度带无解。

**0 套的文案边界：** 只写「严格档无解」，不能写「完全配不出」——`/outfits` 可能仍返回放宽档结果。缺口页要补一句「放宽后能凑合，但不成立」，与列表页的横幅口径一致。

### 9.4 槽位瓶颈

两个维度，任一越线即缺口：

| 参数 | 值 | 含义 | 依据 |
|---|---|---|---|
| `REQUIRED_SLOT_MIN` | 4 | 必需槽（内层 / 下装 / 鞋）可穿件数下限 | 一周 7 天、单件最多穿 2 次 → 至少 4 件才排得开 |
| `OPTIONAL_SLOT_MIN` | 2 | 可选槽（中层 / 外层 / 配饰）下限 | 1 件等于没有选择；洗了这层就消失 |
| `DEP_THRESHOLD` | 0.40 | 单件依赖度上限 | 去掉一件就少四成套数 = 单点故障 |

- `n_S`：能占槽位 S 的单品数
- `dep_S(b) = max_{x∈S} (1 - |V_{-x}(b)| / |V(b)|)`，`V_{-x}` 是删掉 x 后重算的 V；取所有非空温度带的最大值
- `V_{-x}(b)` 由 `C(b)` 过滤掉含 x 的候选后重跑去重，不重新枚举（§9.7 的 `C(b)` 同一份缓存）
- `thin_S = max(0, (MIN_S - n_S) / MIN_S)`
- `dep_score_S = max(0, (dep_S - DEP_THRESHOLD) / DEP_THRESHOLD)`，clamp 1
- `severity = thin_S + dep_score_S`，只用于区块内排序，不跨区块比较

输出必须带上「哪一件在扛」：`dep_S` 的 argmax 单品 + 它所在的温度带。例：「冷天 13 套里有 7 套用黑色薄外套夹克，删掉剩 6 套（-54%）」。

**同一件压两个槽位时合并成一张卡。** 夹克可放 `mid_layer` 和 `outer_layer`；两个槽位的 argmax 是同一件时分开列，会把同一件库存重复算两次。合并规则：`slots` 用列表、`item_count` 取各槽最小值（约束最紧的那个）、`severity` 取各槽最大值，文案点名它能顶的槽位。真实衣柜 18 件的结果是两张卡：黑色薄外套夹克（中层 / 外层，外层只有 2 件，冷天依赖 54%）、灰色运动裤（下装 3 件，凉天依赖 42%）。

**配饰 0 件不单独判瓶颈。** 配饰不参与任何必需组合，`n_S=0` 时按公式会得到 `thin=1`，让每个没有配饰的衣柜都永久挂一张「配饰缺 2 件」的卡。可选槽只在 `n_S>0` 时诊断；中层与外层例外——`R-OCC-01` 在冷天要求两者都存在，0 件会直接表现为温度覆盖 0 套，所以仍按 2 件下限出卡。

**为什么不用「某槽位只占全库 16%」这类比例：** 槽位天然不等量（内层多、外层少），比例会把所有衣柜都判成外层瓶颈。用「件数下限 + 单件依赖度」两个绝对量，才对应真实后果：没得选，或洗一件就崩。

### 9.5 穿不进组合的单品

三类，按优先级：

1. **硬孤立**：所有温度带 `|V_x| = 0`。`placements_of()` 为空的单品直接算硬孤立（属性没填完整，进不了任何槽位）。最严重，单独列出。
2. **边缘单品**：在所有它出现过的温度带里 `support_b(x) < 0.30`，其中
   `support_b(x) = |V_x(b)| / max_{y ∈ 同槽, |V_y(b)| > 0} |V_y(b)|`
   即「和同槽最好用的那件比，出场不到三成」。multi-slot 单品（夹克 `mid+outer`）逐 placement 计算，取最宽松的一个，避免因为某一个槽位竞争激烈就被误判。
3. **正式度孤岛**：`span_ok(x) = |{y ≠ x : |frm(x) - frm(y)| ≤ 2}| / (N - 1) < 0.50`。
   `R-FRM-02` 的极差上限就是 2；超过一半单品与它差 >2，说明它天然只能配少数几件。

每条附一个**主因规则**：在所有含 x 的槽位合法候选里，统计硬规则 FAIL 次数最多的那条（`R-COL-06`、`R-FRM-02` 等），文案直接引用规则的 reason，不另写解释。

**为什么 support 取「每个它出现的带都 <0.30」而不是平均：** 冬季外套在夏天本来就不出场，平均会把季节性单品误判成废件。它只要在能穿的季节里被正常使用，就不是缺口。因此判定必须「在它出现过的每个带里都低于阈值」，只有一个带弱不算：实测黑色速干T恤 凉带 0.29、暖带 0.82，不判边缘。分母只取与当前 placement 有交集的同槽单品；多槽单品逐 placement 算完取最大值。

**没有就不编。** 一条都没有时，页面明确写「没有穿不进任何组合的单品」，不展示空区块。

### 9.6 场合适配缺口

| | |
|---|---|
| 指标 | `best_mean(o, b) = max_{a ∈ V(b)} mean(主件正式度)`，主件 = 内 / 中 / 外 / 下装 / 鞋；输出 `best_formality(o) = max_b best_mean(o, b)` |
| 目标 | `OCCASION_FORMALITY[o]`，直接引用 `R-OCC-02` 的区间，不新造阈值 |
| 判定 | `best_formality(o) < lo` 即缺口（等价于四个温度带都不达标） |
| 证据 | `fit_rate(o) = Σ_b \|{a ∈ V(b) : R-OCC-02 PASS}\| / Σ_b \|V(b)\|` |

同时列出**卡住的槽位**：`max_frm(S) < lo` 的槽位。文案：「见人要求正式度 3.5–4.5；当前内层上限 2、中层 3、外层 3、下装 2、鞋 3，五个槽位都够不到 3.5」。

严重度 `severity = min(1, (lo - best_formality) / 2)`：差 2 档即视为最严重。同样只用于区块内排序。

这条不是硬缺口——组合仍然出得来，只是没有一套符合场合。文案不能写成「无解」。缺口文案给**最低配置要求**，例如「见人至少需要正式度 ≥4 的内搭 / 下装 / 鞋各一件」，不写「补一件就行」。

### 9.7 补齐模拟

**只模拟被诊断出的瓶颈槽位**（最多 2 个；中层/外层合并卡只按约束最紧的外层生成原型，不给中层单独出卡），不生成商品目录，也不模拟场合缺口（理由见本节末）。

原型网格：

| 轴 | 取值 |
|---|---|
| 颜色 | 该槽位映射到 4 色中性调色板（黑 `#141414` / 灰 `#6B7280` / 藏蓝 `#1F2A44` / 米白 `#E8E2D6`）后出现最多的 1 个 + 未出现且与前者 ΔE00 最大的 1 个 |
| 正式度 | 槽位现有范围 ±1（clamp 1–5） |
| 厚度 | thin / medium / thick；鞋固定 medium |
| 版型 / 图案 | regular / solid |
| 品类 | 内层 → T恤，中层 → 卫衣，外层 → 外套，下装 → 裤子，鞋 → 鞋 |

正式度按槽位现有范围 ±1 收窄后，每槽通常 ≤ 18 个原型（2 色 × 3 正式度 × 3 厚度），两个槽合计 ≤ 36 个。若展开后超过 3 档，只取离槽位现有均值最近的 3 档（同距取低档），保证单槽不突破 18 个；槽位一件都没有时，正式度取 2–3。

**正式度为什么要收窄：** 外层现有两件都是正式度 3，补一件正式度 1 的夹克在解锁数上也能加分，但和现有风格不是一条线。诊断只回答「补哪一类」，不应把风格带偏。

**精确算法：缓存严格档候选，只增量枚举新原型。**

4 次全量枚举时保留 `C(b)`（去重前的、所有 `level == 0` 的候选），`V(b) = dedup(C(b))`。对原型 x 只枚举含它的候选：

```
C_x(b) = { c ∈ enumerate_candidates(items, anchor=x) | assess(c, 日常, b).level == 0 }
unlock(b) = |dedup(C(b) ∪ C_x(b))| - |V(b)|
```

这里必须用 `C(b)`（含被去重跳过的旧候选），不能用 `V(b) ∪ C_x(b)` 近似：新原型挤掉一套旧组合后，原先因与那套冲突而被跳过的候选可能重新入选，合并已去重的 `V(b)` 会低估。实测一条灰色中性直筒裤（`#6B7280`），近似算法 `-1/2/25/17`、合计 +43；精确算法 `3/14/25/17`、合计 +59。去重必须用完整候选重跑，**所有展示数字都取精确值**。

**单带可以为负。** 新组合挤掉旧组合时，某个温度带的解锁数可能小于 0；只要 `total_unlock ≥ 5` 且至少 2 个带为正就入选，界面上照实显示负号。

**入选门槛：** `total_unlock = Σ_b unlock(b) ≥ 5`，且至少 2 个温度带 `unlock(b) > 0`。

**入选与排序：** 只从被诊断的槽位（瓶颈，最多 2 个）各取 1 个原型，按精确 `total_unlock` 降序输出，最多 2 条。**场合缺口不在这里模拟**：一件正式单品改变不了 `best_mean`，硬凑一张「补这件就够」的卡是假承诺。场合缺口按 §9.6 列出卡住的槽位与目标正式度，文案写「至少需要正式度 ≥4 的内搭 / 下装 / 鞋各一件」。

**输出措辞固定为「若补一件 ___，___ 套 → ___ 套」**，不出现「买」「推荐品牌」「链接」。

**为什么不在补齐模拟里给场合三件套：** 三件以上组合的枚举与贡献拆分是另一个量级，而且「补一件正式内层」单独看没有意义——三件一起换才可能把 `best_mean` 抬进区间。拆开模拟会制造假精确。场合区块只给最低配置要求，单品级的新衣判断留到 V2。

### 9.9 性能与缓存

- 成本 = 4 次全量枚举（每带一次）+ ≤ 36 次锚定枚举（每个原型一次）+ 18 次去一件重算。18 件实测：4 带全量枚举 + assess + 去重 0.32s；18 件 × 4 带的去一件重算合计 0.13s；单个原型的锚定枚举 4 带 0.13s；复用 `C(b)` 后的精确去重 0.015s。当前路径首次约 5.5s。
- 缓存 `C(b)`（去重前的严格档候选）与最终结果。补齐模拟直接复用 `C(b)`，不重跑全量枚举；缓存键按 confirmed 单品的 id + 参与诊断的属性字段做哈希，任何单品写入即失效。
- 优化顺序：① 只跑硬规则、遇到第一条 FAIL 立即返回，并把 `R-OCC-01` 放最前（它是温度带的唯一入口，能剪掉大部分候选）；② 去重用「两两配对 → 已选组合」倒排索引，避免 O(n²)；③ 原型网格按槽位裁剪（正式度 ±1 收窄、颜色只留 2 个）。
- 预算：18 件首次 ≤ 6s、40 件首次 ≤ 15s、缓存命中 ≤ 50ms；优化后目标 18 件 ≤ 2s。超预算时先砍原型网格（颜色降到 1 个、厚度只留 medium），不砍诊断口径。

### 9.10 测试要求

- 每个阈值至少一组「刚好越线 / 刚好不越线」用例。
- `V` 与 `/api/outfits` 在相同上下文下的严格档结果一致。
- 精确 `unlock` 与「加一件后重跑全量枚举」逐带相等（误差 0）——这是补齐模拟的正确性锚点。固定对照用例：灰色中性直筒裤（`#6B7280`）的近似值 `-1/2/25/17`（合计 43）必须与精确值 `3/14/25/17`（合计 59）不同，防止有人把近似值接回展示层。
- 多槽合并：构造两件 `mid+outer` 夹克，断言只输出一张瓶颈卡，`item_count` 取外层。
- 边缘单品的季节性：构造「凉带 0.29 / 暖带 0.82」的单品，断言不判边缘。
- 硬孤立 / 边缘单品 / 正式度孤岛各一组构造数据。
- 真实 18 件回归基线（2026-10-26 实测）：`V` = 13 / 31 / 71 / 49；见人 `best_formality` = 2.50（凉带）、`fit_rate` = 0；无硬孤立、无边缘单品、无正式度孤岛；两张瓶颈卡（中层+外层合并 `dep` = 0.54、下装 `dep` = 0.42）；补齐第 1 名精确值：薄中性直筒裤 13/31/71/49 → 16/45/96/66（+59）。数字变化必须能解释，不能悄悄漂移。

### 9.11 与 M1 其他部分的关系

- 不复用 `rotation`：缺口与穿着频率无关。
- 不写反馈：诊断是只读的。
- 不新增表：全部由 `item` 现算。
- `/outfits` 全灭时，空状态按钮跳 `/gaps`，可带上当前场合与温度带用于高亮（M1 可先只跳转）。

**这块比"给你 37 套"更值钱** —— 它决定下一件买什么，也就是把衣柜从库存变成系统。也是 V2（买新衣服匹配）的天然入口。
