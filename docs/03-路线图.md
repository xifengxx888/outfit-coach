# 03 · 路线图

> 分期原则：**每一期结束都要有一个能用的东西。** 不允许出现"做了两个月还看不到结果"的阶段。

---

## 总览

| 期 | 交付 | 周期 | 结束时能干什么 |
|---|---|:--:|---|
| **M1** | 录入 + 规则求解 + A 视图 + 缺口诊断 + 每日建议 + 反馈采集 | 2–3 周 | 第一次看到"我的衣柜能搭出哪些套" |
| **M2** | B 档合身图 + 三视图切换 | 3 周 | 看到穿在自己身上的样子 |
| **M3** | 30 天教学 + 判题 | 2 周 | 边用边学 |
| **M4** | C 档生成式 + 规则权重自适应 | 1–2 周 | 完整形态 |

依赖关系是**严格串行**的：M1 的规则引擎是 M2/M3/M4 的共同底座。

---

## M1 · 能用

> 界面规格见 `06-界面与交互.md`。开工前必须走完 `07-开工前检查.md`：六项全部通过才创建 `src/`。

### 范围

| 模块 | 内容 |
|---|---|
| 录入 | 手机拍照留档 → 属性**人工**录入 → 尺寸**手量** → 入库；照片不估尺寸、不做属性提取（见 `07` 第五节） |
| 数据 | SQLite：item / profile / feedback / location / climate_profile |
| 地点与气候 | 地址 → 经纬度 → 近 10 年温度曲线（缓存）→ 当前体感温度区间；`/setup` 首次引导与 `/settings` 地点管理 |
| 首次设置 | `/setup`：地点 + 九项身材，均可跳过；完成或跳过后不再打扰 |
| 我的 | `/settings`：地点、身材、属性提取状态、数据导出（DB 快照 + 照片清单，不含照片）、关于 |
| 规则引擎 | `src/rules/`，纯函数，9 模块 26 条规则（返回值三态：pass / skip / fail） |
| 求解 | 槽位展开 → 暴力枚举 → 硬过滤 → 软评分 → 渐进放宽 → 多样性去重 |
| 锚定求解 | 选中一件 → 只枚举其余槽位 → 共用同一批规则 |
| A 视图 | 单品图横排拼图 |
| 缺口诊断 | 温度覆盖、槽位瓶颈、穿不进组合的单品、场合适配、补齐后解锁数 |
| 每日建议 | 手动生成 + 穿着轮换；今日天气条（实时体感/离线同期/未设地点）。Web Push **待独立一轮**（需 HTTPS/secure context + 订阅存储） |
| 反馈 | adopt / swap / veto_item / favorite / ignore 五路采集 |

### 验收标准

1. 我能把 ≥30 件真实单品录入完毕，且**每件属性我确认过**
2. 任意一份组合，我能从 `explanation` 里看懂它为什么成立：有结论、有具体证据、有理论依据、有「下次怎么自己看」；每条解释都能追溯到实际命中的规则 ID。`reason` 仍保留为兼容字段
3. 缺口诊断能指出至少一个我原本没意识到的瓶颈
4. 连续 3 天生成建议，我能至少采纳 1 套
5. 规则引擎单测覆盖率：每条规则至少 1 个通过/1 个不通过用例
6. 换一个地点（如旅游城市），搭配结果自动按当地温度变化（已覆盖：默认地点切换 + 天气体感）
7. 选中任意一件单品，能在 3 秒内给出至少 3 套包含它的合法搭配
8. 硬规则全灭时，系统给出放宽档位并明确标注，而不是返回空白

### M1 是全局验证点

> 如果规则引擎给出的组合我自己都不认，那 B 档、教学、推送全是给错答案加装饰。

所以 M1 结束必须先停下来评估，再决定要不要进 M2。

### 明确不做

- 抠图、关键点、图像合成（M2）
- 大模型参与排序（M1 只做规则，保持可复现）
- 任何账号体系、云同步
- 上架、分享到社交平台

---

## M2 · 看得见

### 范围

1. 基准照拍摄引导（白墙、正面、全身、贴身浅色衣）
2. 单品抠图（白背景阈值分割为主，rembg 兜底）
3. 人体关键点（MediaPipe Pose）
4. 分层形变对齐 + z-order 叠加 → B 档合身图
5. 前端三视图切换（此时 C 未上线，占位）

### 验收标准

1. B 档图能辨认出是我、能辨认出是哪几件衣服
2. 色彩与原图偏差肉眼可接受（色卡校正链路验证）
3. 生成一套 B 档图 < 3 秒
4. 我能仅凭 B 档图判断"这套成立/不成立"

### 明确不做

- 物理布料模拟
- 生成式试穿

---

## M3 · 学会

### 范围

1. 8 模块 30 节课程内容
2. 每节课绑定对应规则 ID，例题取自我的真实单品
3. 判题：从我的库里挑 3–4 件，问我成不成立，用同一规则判分

### 验收标准

1. 每节课都能用我自己的衣服举例
2. 判题结果与求解器结论**一致**（同一套规则，不允许两套实现）
3. 30 天走完后，我能不看理由直接判断一套搭配成立与否

### 内容工作量 > 工程工作量

这一期的时间主要花在写课上，不是写代码。写不出来说明规则本身没想清楚——回头改规则。

---

## M4 · 完整

### 范围

1. C 档生成式试穿（接现成 API，不做自研）
2. 规则权重自适应（采纳数据微调）
3. 反馈数据看板：哪些规则在起作用、我偏好的实际形态
4. **穿搭公式自动发现**：同一核心组合出现 ≥3 次且反馈为积极 → 固化成一条命名公式（如"深色通勤""大地色休闲"），在建议里优先呈现

> 第 4 项比单纯调权重更值得做：它可展示、可教学，而且用的正是 M1 就开始积累的反馈数据。

### 为什么自适应必须放最后

它需要先积累采纳数据。放在前面等于用空数据调权重，是负收益。

### 验收标准

1. C 档图仅用于确认和分享，界面上必须标注"效果图为生成，可能美化"
2. 调整后的权重有 ≥5 次样本支撑
3. 权重调整前后，我对组合的满意度可对比

## 之后：未来开发计划（V2 / V3，不在当前路线图内）

当前版本做完、并且 M1–M4 的验收都通过之后，再逐项评估。**这些是计划，不是被否掉的方向。**

| 阶段 | 计划 | 内容 | 前置条件 |
|---|---|---|---|
| V2 | 新衣匹配 | 发链接或图片 → 判断能否与现有衣库配、该买什么 | M1 的规则引擎 + 缺口诊断已跑通 |
| V2 | 风格扩展 | 更多场合、更多风格方向（不只三个） | M1 的规则稳定，且我有足够库存支撑 |
| V3 | 性别扩展 | 从"男士专属"扩到通用，或另开女性版本 | 男性版验证通过；身体数据与版型基准需重做一套 |
| V3 | 博主生态 | 博主一键导入风格/设计并发布，用户消费，形成双边 | 有内容供给与冷启动方案；单人项目现阶段做不了 |
| V3 | 网购决策 | 结合个人审美 + 身材 + 已有衣库的购买建议（Buy / Skip / Only if） | 新衣匹配先跑通 |
| V3 | 社交分享 | 把一套搭配生成图片分享到社交平台 | 有值得分享的东西；分享不能反向绑架功能范围 |
| V3 | 盈利与推广 | 变现路径、冷启动 | 前几项有真实用户 |

**V1 阶段任何为这些提前增加的成本，都要被挡住。** 但挡的是时机，不是方向。
