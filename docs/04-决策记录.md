| 2026-10-25 | 流行色进课程，不进算法 | 我的库存是旧的，流行色跟我无关 |
| 2026-10-25 | PWA 起步，不上架 | 拍照与分享 PWA 都能满足 |
| 2026-10-25 | 偏好调整先只做标签，不改规则 | 可逆、不改架构、能积累偏好画像 |
| 2026-10-25 | 身体数据：**量人与量衣都做** | 两者解决不同问题——量人给身体基准，量衣给版型基准。缺任一端，"外套落在胯还是大腿中段"都算不出来 |
| 2026-10-25 | 尺寸按品类分级量取 | 外套 4 项 / 裤子 4 项（裤长、平铺腰围、臀围、脚口宽）/ 内层不量。内层数量最多，全量会让录入成本翻倍，其长度又多被外层遮挡 |
| 2026-10-25 | 裤子尺寸从 2 项扩到 4 项 | 只有裤长和腰围判断不了胯部松量，也判断不了裤脚与鞋面的覆盖关系；臀围和脚口都是平铺直量，一条裤子多花约 1 分钟 |
| 2026-10-25 | 季节改为**温度区间** | 季节标签模糊（"10 月底算秋还是冬"），温度可计算且直接对应衣服厚度 |
| 2026-10-25 | 地址 → 近 10 年气候 → 当前温度 | 同一天哈尔滨与三亚是两套穿法；旅游换城市时自动适配 |
| 2026-10-26 | 标定卡允许用**实测尺长**做比例基准，不强制打印 100% | 打印店无法控制缩放；卡上自带 100mm 尺，实测 `L` 后按 `L/100` 换算即可，前提是横竖等比。避免把打印机设置变成开工阻塞 |
| 2026-10-26 | 照片自动估尺寸**不进 M1**，M1 全部手量 | 9 张标定照实测（`scripts/spike/gate1_result.json`）：正拍衣长误差 +0.95 / +1.80cm，偏 15° +4.4 / +7.2cm，偏 30° +9.4 / +13.4cm；裤长误差 +8.0cm，因为真值定义是沿侧缝的弧线，平铺轮廓既量不出弧长也给不出两端。三条根因：卡上 48.5mm 的 ArUco 只占画面 37–59px，±1px 角点误差即 2% 尺度误差；仿射无法纠正离标记 20–40cm 处的透视（误差随 tanθ 增长）；端点定义与轮廓不等价。**标定失败不阻塞 M1——手量本来就是必做项** |
| 2026-10-26 | 用标记四角拟合**单应**替代仿射的方案被否 | 近正方形小四边形（37–59px）的透视项条件数太差，拟合结果失稳：4.0 照片反而少算 9.3cm。把六个色块一起做 10 点拟合也不行——色块在卡上的实际位置与标称值差 1–2mm，会引入 1%–3% 的尺度各向异性。现有数据不支持在这么小的基线上估透视 |
| 2026-10-26 | 新增 `daily_suggestion` 表记录当天展示的组合 | 次日补记 `ignore` 需要知道昨天展示了哪一套；`feedback` 只存 hash 与信号，无法反推展示记录。一天一行，补记后删除，不参与求解 |
| 2026-10-26 | 缺口诊断以「严格档 + 去重后」为口径 | 放宽档是「凑合穿」，用它统计会让所有缺口消失。只有严格档 + 与列表页同一套去重，才能回答「缺什么」 |
| 2026-10-26 | 缺口按四个温度带代表值（5/14/22/30°C）全局分析，不做单上下文 | `R-OCC-01` 只认区间，带内严格档结果恒定；10/18/26 边界处阶跃且放宽容差会跨带取值，取带内点才有解释力。场合规则是软规则，不影响可解性，每带只求解一次 |
| 2026-10-26 | 瓶颈 = 件数下限 + 单件依赖度，不用槽位占比 | 槽位天然不等量（内层多、外层少），比例会把每个衣柜都判成外层瓶颈。绝对量才对应真实后果：没得选，或洗一件就崩 |
| 2026-10-26 | 补齐模拟只生成「槽位 × 正式度 × 厚度 × 中性色」的有限原型，不接商品库 | 越界到购物推荐会绑架 M1 范围；原型只回答「补哪一类、能多解锁多少套」，不回答买哪个牌子 |
| 2026-10-26 | 缺口阈值：每带 ≥10 套、必需槽 ≥4 件、可选槽 ≥2 件、单件依赖 ≤40%、边缘单品 <30%、正式度孤岛 <50% | 10 套 = 两周不重样；4 件 = 单件一周最多穿 2 次；依赖 40% = 失去一件即失去四成套数；30% = 不到同槽头名的三成；50% = 与半数以上单品正式度差 >2，会被 `R-FRM-02` 持续拦下 |
| 2026-10-26 | 补齐解锁数用**完整候选集**重跑去重，不用已去重的 `V` 合并 | 新组合挤掉一套旧组合后，原先因与那套冲突而被跳过的候选可能重新入选，合并 `V` 会低估。实测中性直筒裤：近似 `-1/2/25/17`（+43） vs 精确 `3/14/25/17`（+59） |
| 2026-10-26 | 补齐原型只做数量型，正式度限制在槽位现有范围 ±1；场合缺口不做单品模拟 | 外层现有两件都是正式度 3，补正式度 1 的夹克在数字上也能加分，但会把风格带偏。场合缺口要三件以上一起换才可能把 `best_mean` 抬进区间，单件模拟是假精确 |
| 2026-10-26 | 同一件单品压多个槽位时，瓶颈只出一张卡 | 夹克同时顶中层和外层，分开列会把同一件库存重复计算；件数取最紧的槽位，依赖度取各槽最大值 |
| 2026-10-26 | 录入页做**单页表单**，不做三步向导 | 照片不再标定/估尺寸，拍照独立成步已无价值；单页 + 吸底保存栏更接近「熟练后 30 秒/件」。分步还会让「中途退出存草稿」变成额外状态 |
| 2026-10-26 | **照片不阻塞 `confirmed`** | `photo_path` 可为空，规则求解完全不读照片，`confirmed` 的语义是「属性齐 + 条件尺寸齐」。相机失败或隐私顾虑不该卡住入库；无照片时按钮写「无图入库」，衣库显示占位 |
| 2026-10-26 | 新照片写 `data/photos/`，旧 `pic/` 只读 | 旧 18 件是真实衣柜且分散在两个目录约定下；移动/重写会带来丢图风险，收益为零。新文件用 `secrets.token_hex` 随机名，两个目录各挂静态路由 |
| 2026-10-26 | 照片走 JSON base64，不引 `python-multipart` | 服务端已有 Pillow 可校验；为一种上传格式新增依赖不值。客户端先用 `<img>` 解码（浏览器应用 EXIF 方向）再压到最长边 1600，服务端再 `exif_transpose`、转 RGB、去 EXIF，上限解码后 8MB / 40MP |
| 2026-10-26 | M1 底部导航是 **衣库 / 组合 / 今日** 三列，`/settings` 落地后扩为四列（衣库 / 组合 / 今日 / 我的） | 衣库与录入先落地；「我的」随 `/settings` 一起加，避免先摆一个空页签 |
| 2026-10-26 | 草稿补完放到 `/item/:id`，录入页不做补完入口 | 补完需要读回全部字段并 PATCH，等于半个编辑页；本轮先诚实标注「待补完 · 暂不参与搭配」，不放假入口 |
| 2026-10-26 | 单品详情用 `GET /api/items/{id}`，编辑与状态变更共用一个 `PATCH`，合并后复用 `ItemIn` 校验 | 详情需要尺寸与季节，列表接口保持轻量；编辑若另写一套校验，迟早与录入口径分叉。`PATCH` 只传变化字段，归档与重新启用也走同一端点 |
| 2026-10-26 | 已有照片只读；编辑只能给无照片单品补第一张 | 替换会留下无引用的孤儿文件，删除直接违反「不删原图」红线；M1 的价值在属性与尺寸，照片留档一次就够 |
| 2026-10-26 | 详情页不显示累计穿着次数，只显示 `last_worn_at` | adopt 的 `feedback` 只存整套 hash，没有单件穿着流水；要统计必须加表，属于 M1 之外的 schema 变更。数字宁缺勿假 |
| 2026-10-26 | 锚定页保留场合/温度栏；放宽结果只列前 3 套 | 锚定求解同样吃 `Context`，天气未接入时不给调节会让结果像凭空出现。放宽档是「凑合穿」，三套足够判断且避免无限翻页 |
| 2026-10-26 | `needs_setup = profile 无 id=1 行 且 location 为空`，跳过向导写入一行空 profile | 不为一个引导标记改 schema；双条件保证只存身材或只加地点后都不再打扰；`ON CONFLICT DO NOTHING` 不覆盖已有资料 |
| 2026-10-26 | 添加地点时同步拉十年气候，失败不阻塞保存，`/settings` 可重取 | 十年曲线让离线也能给温度；把失败变成「地点没加上」会把一次网络抖动升级成数据丢失。实时天气先可用，气候后补 |
| 2026-10-26 | 九项身材全部存储，本轮只有 `height` 进入 `Context.height_cm` | 规则层目前只有 `R-PRP-04` 消费身高；把另外八项标成「已参与」是假功能。`estimated` 不排除，符合「只降权不排除」 |
| 2026-10-26 | 数据导出只给 DB 快照 + 照片清单，不给照片二进制 | 导出目的是备份与迁移属性数据；把 19MB 原图塞进 zip 既慢又扩大泄露面。清单带 SHA-256 可校验原图是否齐全 |
| 2026-10-26 | Web Push 延后到独立一轮 | 订阅需要持久化（schema 或文件），且手机走局域网 HTTP 不是 secure context，无法订阅；VAPID 与定时器另算。先把地点/天气/设置闭环，避免半成品开关 |
| 2026-10-26 | 新增 `R-SIZ-01` / `R-SIZ-02` 两条复合软规则，不做硬排除 | 身材来源可能含估算、衣件尺寸也常缺；硬过滤会把「没量」误判成「不能穿」，而当前痛点是结果太少。软扣分能看见不合身，又不砍掉候选 |
| 2026-10-26 | 本轮接入肩宽/胸围/臀围/臂长（连同已有身高）；腰围、内长、颈围、体重延后 | 腰围受低腰与弹力腰头影响，运动裤平铺 32×2=64cm 对身体 81cm，规则会误判实际在穿的裤子；衣件只有外长（95–96cm），没有内缝字段可比身体内长 67cm；颈围、体重没有对应的衣件字段或可靠规则 |
| 2026-10-26 | 理由上限 4→5，`siz` 排在软规则顺序最前 | 两条身形理由要稳定占位，同时给颜色/场合留 3 条；软规则顺序即理由顺序（`SOFT_RULES` 按 `MODULES` 生成）。每条复合规则只出一条理由且内部不用 `；`，避免挤掉其他理由 |
| 2026-10-26 | T恤/衬衫/卫衣的肩宽、胸宽必填，袖长选填 | 肩/胸是 `R-SIZ-01` 的两个主维度，缺一项整套就少一条身形理由；袖长只判长袖（≥40cm），短袖不量也不影响，强制会让录入变慢。缺肩/胸只能存草稿，缺袖长仍可 `confirmed` |
| 2026-10-26 | 衣件平铺尺寸的前端标签统一写「平铺」，hint 注明「不乘 2」，系统比较时 ×2 | 现有标签写「腰围/臀围一圈」，但库里存的是平铺半围（腰头平量 32cm 即 64cm 围度）。标签不改，录入手感与规则口径会长期对不上 |
| 2026-10-26 | 每件最多 **6 张照片**，第一张即封面，不分用途、不打标签 | 多角度照片是录入时最便宜的补充信息，但角色标签会带来「这张算不算封面」的额外状态；首图封面是唯一需要说清的规则。6 张 = 正面 + 背面 + 细节，超过只会拖慢提交 |
| 2026-10-26 | **已存照片永不删除**；编辑页只读已有图，只能追加新图，不提供替换、删除、排序、改封面 | 替换会留下无引用孤儿文件，删除直接违反「不删原图」红线。上一轮「编辑只能给无照片单品补第一张」由本条取代，其余（已有图只读）不变 |
| 2026-10-26 | 追加照片存 `item.extra_photos`（JSON 数组列），不新建 `item_photo` 表 | 单用户、每件 ≤6、无角色无排序需求，一张表一次 JOIN 都不需要。JSON 列与 `layers`/`seasons` 用同一套仓储读写习惯；将来要角色或时间戳再拆表 |
| 2026-10-26 | **衣长对全部上衣必填**（T恤/衬衫/卫衣/**毛衣/针织**），排在尺寸区第一项 | 衣长是 `R-LYR-02` 与 `R-PRP-04` 的输入，也是「下摆落点」的唯一依据；之前只对三种上装开放录入，毛衣/针织与它们同处内层槽位却少一个维度，同槽单品的理由条数不对等。现有 9 件上衣的衣长早已量过，无补量成本 |
| 2026-10-26 | 鞋新增 **EU 鞋码**，必填（`confirmed`），但 M1 **只存档、不参与任何规则** | 没有可靠的「鞋码 → 合脚/显腿长」规则可编码，硬造一条就是假精确；但这是录入时最容易忘、事后最难补的数据，先在填表时收齐。详情页显示「42 码」，求解结果不受影响 |
| 2026-10-26 | 取色给三个入口：16 个预设、系统调色板（`<input type="color">`）、照片点选 5×5 平均；HEX 输入保留 | 主色常常不在预设里，手机端又不可能去开设计软件吸色。照片点选是「看到哪点哪」，5×5 平均能压掉面料纹理和噪点；原生调色板在部分 iOS 版本表现不一，HEX 与预设始终是兜底 |
| 2026-10-27 | `reason` 原样保留，新增结构化 `explanation`，不重写 `_build_reason` | 25 条规则文案测试与 `test_settings_api.py` 依赖现有 reason 的文字与顺序；把解释另起一层，既不动判定，也不破坏兼容。前端可回退到 `reason` |
| 2026-10-27 | 理论库双落地：`docs/11-搭配理论库.md` + `src/rules/theory.py`，并新增只读 `/theory` 页 | 文档给人审阅，代码给解释器取元数据，页面给日常查阅。三处同源，避免「解释写得漂亮、代码里没有」 |
| 2026-10-27 | 解释只对最终返回的 1–10 套生成，放在 API 层，不进入 `solve()` / `assess()` | `solve()` 会对上千个候选调用 `assess()`；解释是展示成本，不是求解成本。用 monkeypatch 测试锁住热路径 |
| 2026-10-27 | 18 条原理覆盖 26 条规则，按 A/B/C/D 标注依据等级，五种状态（active/conditional/baseline/boundary/dormant） | 搭配领域大量说法是造型经验，不能包装成科学；当前衣柜只支持部分理论，`dormant` 只在原理页展示，不硬凑进解释 |
| 2026-10-27 | 风格标签只做描述，带「推断」徽标，不参与评分与排序 | 没有 style tags、配饰、鞋型数据，完整风格原型无法判定；四轴（正式度/廓形/色彩/层次）可计算，但只能称为推断 |
| 2026-10-27 | 解释层不调 LLM、不新增规则/阈值/schema，不改照片 | 保持可复现与「每条知识都是真实生效的代码」；风格与偏好数据留到 M2 再评估 |

### 一·补 · 由开源调研确立的决策（2026-10-25）

> 依据见 `05-开源调研.md`。这一批不是推演出来的，是有代码或对照实验支撑的。

| 日期 | 决策 | 理由 / 证据 |
|---|---|---|
| 2026-10-25 | 规则优先，学习层只做排序微调 | `loom` 用 620 件 H&M、1 万道 FITB 题做对照：规则打分换成学习打分器后 recall@1 0.509 → 0.424，学习打分器 AUC 0.644 反而低于纯余弦 0.773。学习层不天然优于规则 |
| 2026-10-25 | 色彩必须写成显式规则，不用嵌入替代 | `loom` 删掉显式色彩规则后，色彩冲突率 0.902 → 0.958（更差）；它最后给出的修复方案就是"恢复色彩与互补规则过滤器" |
| 2026-10-25 | 硬过滤后必须带**渐进放宽** | `loom` 保留硬门槛时三套覆盖 2.73 → 2.40，"所有候选都违反硬门槛，直接跳过"。三十件衣服配 24 条规则，全灭是现实风险 |
| 2026-10-25 | 枚举前先展开**身体槽位** | 直接按 `layers` 多值做笛卡尔积会产出"两条裤子""连衣裙配裤子""只有外套没上衣"。方案取自 `wardrowbe` 的 `ROLE_SLOTS` + `deduplicate_by_body_slot()`（MIT，已核实） |
| 2026-10-25 | 输出必须做**多样性去重** | 不做的话，前十套很可能是同一件外套换内搭。取自 `dresser` 的 `_diverse_top()`：与已选共享 ≥3 件即跳过 |
| 2026-10-25 | **锚定求解是一等公民**，不能靠全量枚举后筛 | V1 第三项需求"选中一件 → 配一套"。必须有独立入口，且与全量求解共用同一批规则，否则两种模式会给出互相矛盾的答案 |
| 2026-10-25 | 温度取**体感温度**；档位做硬约束 + 连续目标做软评分 | 气温不含风速湿度；只有硬档位会在 25.9°C / 26.1°C 之间产生断层。连续目标公式取自 `dresser`，体感温度取自 `AIWardrobe` 的实测 |
| 2026-10-25 | `material` 进 M1，且必须**人工选** | `dresser` 在 21 件真实衣服上实测四个 VLM，材质准确率都在 67% 左右（颜色 90–100%）。自动填等于给 R-MAT-01 / R-SHO-03 喂噪声 |
| 2026-10-25 | 学习改成**配对级优先**，规则级次之 | 三十件衣服每天一次反馈，单条规则凑 5 次采纳要很久；"外套 A 配裤子 B"出现得频繁得多，且直接服务锚定求解。公式取自 `wardrowbe`（MIN_PAIRS=5） |
| 2026-10-25 | 六类色彩关系只用于措辞与课程，**不新增规则** | 概念取自 `chromafit`；加规则会让"解释"和"判定"变成两套逻辑 |
| 2026-10-25 | 软色彩规则改用 **CIEDE2000**（ΔE00 <10 / ≥10），硬规则仍用主色数与饱和度 | 裸明度差区分不了深蓝/深灰与米白/浅卡其；硬规则要能被课程讲明白，所以保留可解释的量 |
| 2026-10-25 | 标定从 A4 白纸改为**印刷标定卡**（ArUco + 18% 灰卡） | 白纸边缘在白色背景上不可靠、衣服本身也可能是白的；透视稍歪误差即超 ±2cm。ArUco 同时给尺度与四个角点，估长误差约 ±1cm |
| 2026-10-25 | 拍照只承诺"衣长/裤长可估"，肩宽/胸宽/袖长仍手量 | 实测精度不足时不要承诺。宁少一条自动项，也不要用错数据 |
| 2026-10-25 | 属性提取的 VLM **延后到上线前评估**；M1 默认手动录入，demo 可用当前会话的视觉模型协助预填 | 本地模型需下载 5–6GB，M1/16GB 能否稳定运行未知；云端模型会把衣柜照片上传第三方。demo 只是一次性填表，借用对话模型不构成产品功能，正式度等字段也不参与判定 |

## 二、讨论中被推翻的判断（Claude 的错，记录防重犯）

| 错误判断 | 纠正 |
|---|---|
| "整套（上装+下装+外套+鞋）一次生成不可用" | **2026 年已经可用**。P-Image Try-On 支持 1–11 件，MyEdit/WaveSpeed 支持整套，Google 已上线。外套叠穿有 ECCV 2026 LVTON、ICASSP 2026 GO-MLVTON、IEEE LayerDiffusion 专门攻。是我拿旧认知当结论 |
| "库存太少，建议没有统计意义" | **用词错误**。规则是确定性的，给 8 件就解 8 件，不存在样本量问题。真实存在的只是一个很窄的校准问题（分不清"规则错"和"衣柜出不了好组合"） |
| "推送要先手动点三天建立信任，再开自动推送" | **因果反了**。推送本身就是偏好数据的采集入口，不是信任的结果。已改到 M1 |
| "V1 需要提前知道衣柜品类分布" | **不需要**。算法是通用的。这是把自己的便利转成用户的成本 |
| "冷启动/留存/变现是首要问题" | 用户明确 V1 只服务自己。这三个问题在 V1 不存在，属于 V3 |
| "Wardrobe 的生成式单品图重绘是关键技巧" | 对个人衣柜是**反模式**。它会把我的衣服画成理想状态，破坏真实性 |
| "量衣还是量人"设成二选一 | **不是冲突关系，两者都做**。量人给身体基准，量衣给版型基准，缺一端就算不出外套的落点 |
| `item` 表只有属性字段、没有尺寸字段 | **实质缺口**。R-LYR-02（层次长度差）与 R-PRP-04（外套下摆）当时无数据可跑，建表时才暴露 |
| "`ideas.md` 差异化分析的四项（性别聚焦 / 博主生态 / 网购决策 / 社交分享）已被 V1 否决" | **把"推迟"写成了"否决"，是实质错误。** 用户明确：这四项是未来开发计划，当前版本做完后再逐项评估。已在 `01` 第四节与 `03` 末尾列为 V2/V3 计划 |
| "`tandpfun/wardrobe` 有 2250★，它的做法值得参考" | **星数不改变判断。** 它靠 gpt-image 重绘单品图、且必须上传 OpenAI，两条都命中我们的红线。只有槽位词表可复用 |
| "ChromaFit 的调色板基于 Sanzo Wada《配色辞典》" | **数据是假的。** 实际只有 30 组、114 色，命名是 "Midnight Dusk" 这类现代英文名，色值取自 CSS 命名色。不能当权威用 |
| 首轮开源调研只查了 `wardrowbe` | **覆盖不全。** `ideas.md` 那份清单有 11 项，补查后只有 3 项可用、2 项只值得读文档、3 项查无实据。已补进 `05` 的"二·补" |

## 三、被否掉的方案

| 方案 | 否决理由 |
|---|---|
| AI 男士穿搭顾问（生成式推荐） | 无法复现、无法验证、不可信 |
| 衣橱管理 SaaS | 冷启动成本高，日频低强度需求 |
| **在 V1 就做**博主生态 / 双边市场 | 单人项目现在做不了，V1 用户只有我一个。**否掉的是时机，不是方向**——它作为 V3 计划保留，见 `01` 第四节 |
| 3D 数字人 + 3D 服装 | 技术不成立 |
| 物理布料模拟 | 成本高一个数量级，B 档只需"能判断" |
| 生成式单品图重绘 | 破坏真实性 |
| 流行色驱动推荐 | 库存是旧的 |
| 原生 App 起步 | 上架是分发问题，不是 V1 问题 |
| 提前提供衣柜清单 | 不需要 |
| **把"专注男士"当作核心壁垒** | 性别是定位不是壁垒；男性市场更小但痛点更集中，靠功能而非性别取胜。这不排斥以后做性别扩展（见 `01` V3） |
